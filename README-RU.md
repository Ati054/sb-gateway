# SB Gateway для MikroTik RouterOS 7

SB Gateway — управляемый через браузер прокси-шлюз в одном ARM64-контейнере
RouterOS. Сервер принимает VLESS через WebSocket, gRPC, HTTPUpgrade и XHTTP;
прямой REALITY с XTLS Vision; gRPC + REALITY; XHTTP + REALITY и Hysteria 2.
Единственное proxy-ядро — закреплённый Xray-core 26.9.9 с проверяемыми
локальными исправлениями совместимости и аварийной устойчивости. Шлюз
маршрутизирует выбранные сервисы или весь интернет выбранных локальных клиентов
через внешние VLESS-узлы, Reverse VLESS или выбранные WireGuard-туннели MikroTik и
не заменяет существующие LAN, Wi‑Fi, WireGuard, SSTP, OpenVPN, firewall или
маршруты MikroTik.

Созданные проектом объекты имеют точную метку `SB-GATEWAY`. Единственное
обратимое изменение существующего объекта — `allowed-address` явно выбранного
WireGuard peer: исходное значение сохраняется и возвращается при снятии выбора
или удалении SB Gateway.

Входящий WireGuard-клиент определяется RouterOS peer, а не общим интерфейсом.
Панель сохраняет стабильный `.id` peer и перед Check, Plan и Apply заново
получает его текущие конкретные IPv4-префиксы. Поддерживаются адреса `/32` и
site-to-site сети; `0.0.0.0/0` источником клиента не считается. Смена public key
или адреса у того же объекта не создаёт второго клиента. Удалённый и созданный
заново peer имеет новый `.id`: такая запись блокирует Apply до явного выбора.

Основной способ управления — Web UI. Командная строка `gatewayctl` оставлена
только для аварийного восстановления, когда панель недоступна. Единственный
обязательный подготовительный этап выполняется один раз в WebFig: включение
container device-mode, загрузка образа и запуск безопасного bootstrap-скрипта.
После этого пользователи, сети, подписки, города, обновления, резервные копии,
диагностика, безопасная смена образа, полный scoped-uninstall и откат
настраиваются из панели. Отдельного публичного сайта-заглушки и слушателя
TCP/80 нет. Неизвестный SNI закрывается, а неизвестный путь на уже настроенном
CDN-домене получает нейтральный ответ. Ссылка подписки использует один
случайный сегмент без говорящего префикса.

## Совместимость RouterOS

| Компонент | Поддержка | Политика |
|---|---:|---|
| RouterOS ARM64 | **RouterOS 7 с требуемыми возможностями** | имя канала не является gate; version/channel только определяются |
| Xray-core | **26.9.9** | единственное ядро, зафиксированное на точном commit; локальные patch применяются только к проверенному исходнику и проходят тесты при сборке |
| Платформа | MikroTik ARM64 | hAP ax³ — reference; контейнер и данные — на внешнем SSD |

Long-term, stable, testing, development и другие каналы RouterOS 7 допустимы: Web UI
показывает предупреждение о риске, но имя канала само по себе никогда не
блокирует Apply. Compatibility-gate запрещает **новое применение** только
если capability-preflight не нашёл конкретную необходимую возможность
(containers, kernel TPROXY/nftables, auto-restart, routing/firewall primitives).
Отдельно действуют обычные safety-gates: подтверждение фактических адресов,
обезличенный export, сертификаты, секреты и review.

Проект никогда не меняет канал и не обновляет RouterOS автоматически. Он не
останавливает уже применённую generation из-за изменения metadata. Само
обновление RouterOS обычно перезагружает роутер; после загрузки startup-script
сначала принудительно оставляет локальный трафик на обычном WAN, затем
`start-on-boot`/auto-restart поднимает контейнер, и diversion возвращается
только после hysteresis. Несовместимость запрещает следующую mutation, а не
ломает уже сохранённую конфигурацию.

Apply публикует и перезапускает только действительно изменившиеся runtime-
артефакты: чистое переименование/metadata не трогает Xray и Nginx. Изменения
RouterOS по возможности применяются симметричным delta из целых управляемых
секций, но свежий backup, SSH Safe Mode, rollback-scheduler и health-check
остаются обязательными. Неизвестная структура или слишком большой delta
автоматически переключают операцию на полный candidate.

## Поведение при отказах

| Источник трафика | Нормальная работа | Контейнер недоступен |
|---|---|---|
| Неуправляемый локальный клиент | обычный RouterOS/WAN | без изменений |
| Управляемый локальный/VPN-клиент | сервисные правила или весь интернет через выбранную VPN-политику | для каждого IP отдельно: **обычный WAN** либо **только LAN** |
| Удалённый пользователь шлюза | внутренние сети согласно **Доступу к LAN**, интернет через назначенную политику | **fail-closed**, обычный WAN не используется как неявный резерв |

RouterOS запускает контейнер при загрузке и использует
`restart-policy=always` и `restart-interval=10s` (с fallback на legacy
`auto-restart-interval=10s`). Дополнительный watchdog проверяет не только
состояние контейнера, но и готовность Nginx, выбранного proxy-ядра и сгенерированной
конфигурации. После трёх последовательных ошибок dataplane он отключает только правила
`SB-GATEWAY`, направляющие новые соединения управляемых локальных клиентов в
контейнер. Остальная конфигурация RouterOS не меняется. Возврат происходит
только после трёх успешных проверок; дополнительный cooldown по умолчанию равен
нулю и включается оператором только при необходимости, поэтому краткие колебания не
вызывают постоянных переключений. Временная недоступность только локального
management API снимает readiness lease, но не обрывает исправные Xray/TPROXY/DNS
соединения: принудительный рестарт допускается лишь после 24 последовательных
API-ошибок. Отказ процесса Xray, TCP/UDP TPROXY listener, policy route или DNS сохраняет
быстрый порог.

При загрузке RouterOS и при каждом повторном импорте watchdog diversion gate
немедленно выключается. Внутренний process-watchdog ограничен скользящим
бюджетом (по умолчанию 6 принудительных рестартов за 60 минут). После
исчерпания бюджета контейнер и логи остаются для диагностики через WebFig, а
клиенты с режимом `direct` продолжают работать через обычный WAN, а клиенты с
`lan_only` сохраняют локальную сеть без доступа в интернет.
Web UI при этом доступен только если management API исправен.

Короткий обрыв уже установленных соединений в момент аварии возможен: новые
соединения переходят на прямой WAN после времени обнаружения. Нулевой разрыв
без второго шлюза физически недостижим.

## Архитектура

```text
Интернет
   ├── Cloudflare ── TCP/443 ── RouterOS dst-nat ── Nginx
   │                                              ├── WS → активное ядро :11001
   │                                              ├── gRPC → активное ядро :11002
   │                                              ├── HTTPUpgrade → активное ядро :11003
   │                                              └── XHTTP → активное ядро :11004
   ├── DNS-only ── TCP/2443 ── RouterOS dst-nat ── REALITY/XTLS-Vision
   ├── DNS-only ── TCP/2444 ── RouterOS dst-nat ── gRPC + REALITY
   ├── DNS-only ── TCP/2446 ── RouterOS dst-nat ── XHTTP + REALITY
   ├── DNS-only ── UDP/443 ─── RouterOS dst-nat ── Hysteria 2
   ├── VLESS/REALITY/Hysteria 2 провайдеры ← Xray outbounds
   ├── Reverse VLESS-клиенты ← Xray reverse egress
   └── выбранный WireGuard MikroTik ← отдельная sb-wg-* policy table

LAN / Wi-Fi / WireGuard / SSTP / OpenVPN
   ├── точные внутренние назначения ─────────────→ обычная таблица RouterOS
   └── публичный трафик только SB_MANAGED_CLIENTS
          └── to-sb-gateway → kernel TPROXY
                 ├── выбранный сервис → противоположная сторона маршрута
                 └── остальной интернет → обычный WAN или выбранная VPN-политика
```

Сторона «VPN» в маршрутном листе может содержать обычные VLESS/Hysteria-узлы,
Reverse VLESS и выбранные WireGuard-интерфейсы RouterOS. Для WireGuard панель
сама подготавливает full-tunnel `allowed-address` и отдельную таблицу
`sb-wg-*`, сохраняя исходное значение peer для восстановления. Основной
default route MikroTik при этом не меняется: в WireGuard попадает только трафик
с выделенного source-адреса SB Gateway.

До контейнера не выполняется masquerade: активное proxy-ядро видит исходный адрес
локального клиента и может применить персональную политику. Внутренние
назначения исключаются до policy routing и остаются в основной таблице
RouterOS.

## Первый запуск: WebFig и однократный импорт

Обычная настройка выполняется в Web UI. До его первого запуска необходим
однократный bootstrap через **WebFig Terminal**; SSH/WinBox и постоянная работа
в CLI не нужны.

1. Скачайте `sb-gateway-1.6.17-routeros-bundle.zip` со страницы GitHub Release
   и проверьте SHA-256 архива. Внутри находятся контейнер
   `sb-gateway-1.6.17-linux-arm64.tar`, его checksum и manifest, а также каталог
   `routeros/`. На компьютере отдельно проверьте SHA-256 внутреннего `.tar`.
2. Подключите USB 3.0 SSD и компьютер администратора кабелем к доверенной
   management LAN. Не выполняйте bootstrap через Wi‑Fi или удалённый VPN.
3. В WebFig создайте binary backup и обычный текстовый export, затем скачайте
   оба файла. В **System → Packages** запишите текущие version/channel, не меняя
   их, и убедитесь, что ARM64-пакет `container` совпадает по версии с RouterOS.
4. В WebFig включите container device-mode. RouterOS потребует физическое
   подтверждение кнопкой/питанием и перезагрузку — это штатная защита MikroTik.
5. Проверьте, какие WAN TCP/UDP-порты уже заняты. Несколько CDN hostname могут
   делить TCP/443 по SNI/path, а Hysteria 2 использует UDP и не конфликтует с
   TCP/443. Прямой REALITY и прямой HTTPS на одном public IP:port несовместимы.
   Для RouterOS `www-ssl` выберите отдельный свободный management-порт.
6. Через **Files** создайте каталог на USB SSD, например `usb1/sb-gateway`, и
   загрузите туда проверенный `.tar` и `.rsc`; не используйте внутренний NAND.
   Сделайте приватную копию `variables.example.rsc`, укажите
   `SB_IMAGE_SOURCE="file"`, точный `SB_IMAGE_FILE`, фактические пути/сети и
   временные bootstrap credentials. Только после сверки адресов установите
   `SB_ADDRESSES_CONFIRMED=true`.
7. В **IP → Services** для `www-ssl` укажите выбранный порт/сертификат.
   **Available From** должен содержать ровно фактические IPv4 management CIDR и
   container `/32`, без `0.0.0.0/0`. Те же порт и имя сертификата запишите в
   приватный variables-файл.
8. Загруженный `.rsc` сам не появляется в **System → Scripts**. В **WebFig
   Terminal** один раз выполните
   `/import file-name=<каталог-релиза>/bootstrap.rsc`. Bootstrap проверит
   комплектность файлов, загрузит приватный `variables.rsc`, выполнит
   preflight, создаст отдельную учётную запись REST, проверит FastTrack,
   установит контейнер и watchdog. Скрипт оставляет управляемый трафик на
   обычном WAN до подтверждения готовности выбранных маршрутов.
9. В **Containers** дождитесь состояния `running`, затем откройте
   `https://<фактический-IP-контейнера>:9443` из management LAN. После
   сохранения credentials в secret store удалите приватный variables-файл с
   временными паролями из **Files**.
10. Мастер панели потребует загрузить свежий обычный
   `/export file=sb-gateway-audit` без флага `show-sensitive`,
   подтвердить фактические RouterOS gateway, container IPv4/CIDR, TUN CIDR и
   внутренний DNS, выбрать доверенный LAN-интерфейс, явно принять или
   игнорировать каждую найденную LAN/VPN-сеть, заменить примерные сети/домены,
   сохранить REST credentials
   в secret store, создать остальные секреты, загрузить TLS-пару для выбранного
   CDN origin, проверить candidate-конфиг и создать снимок перед первым
   применением.

Полная последовательность установки находится в [INSTALL-RU.md](docs/INSTALL-RU.md).
Расширенная эксплуатация и восстановление описаны в
[OPERATIONS.md](docs/OPERATIONS.md), а экраны панели — в
[WEB-UI.md](docs/WEB-UI.md).

## Что настраивается в Web UI

- **Обзор**: RouterOS, контейнер, Xray-core, fail-open и компактные строки
  клиентов. Для клиента видны активность, uplink/downlink и месячный трафик.
- **Устройства**: локальные и удалённые пользователи, их точные IP/CIDR,
  `client_tun_address`, доступ к LAN, выбранные транспорты и клиентские ссылки.
- **Маршрутизация**: листы `VLESS + WAN` и `WAN + VLESS`, сервисные карточки
  из доверенного каталога, VLESS/Reverse/WireGuard-выходы, приоритеты и качество
  узлов за 24 часа, 7 или 30 дней. WAN и VPN используют независимые DNS-линии;
  DNS-запрос и соединение сервиса следуют одному выходу. Полный клиентский
  профиль раскрывает составную карточку в существующие `geosite`/`GEOSITE`-
  теги и fallback-домены по таблице в [CLIENTS.md](docs/CLIENTS.md#как-карточки-попадают-в-клиентский-профиль).
- **Подключения**: провайдерские подписки, узлы, TLS-профили, прямые REALITY и
  Hysteria 2, CDN-развёртывания и Reverse VLESS. Каждое CDN-развёртывание имеет
  собственные distribution hostname, SNI, origin, TLS и защиту origin.
  Клиентская HTTPS-подписка имеет три сценария: через CDN, напрямую по HTTPS
  или одновременно по обоим адресам. В сценарии CDN можно создать отдельный
  домен подписки либо выбрать уже настроенное CDN-развёртывание без нового
  WAN-порта. Один URL автоматически выдаёт
  URI/base64, полный Xray JSON или Mihomo YAML; в полном профиле доступны
  индивидуальные исключения, раздельный шифрованный DNS, fallback узлов,
  консервативный AdBlock и сохранение локальной сети устройства.
- **Эксплуатация**: проверки, rollback, один ARM64 `.tar` с автоматическим
  возвратом, полное удаление и до трёх зашифрованных `.sbgw` на SSD. До трёх
  зеркал в RouterOS Files создаются асинхронно и не блокируют обновление.
  Архив можно скачать, загрузить и восстановить через браузер.
- **Настройки**: доступ к панели, смена пароля, RouterOS integration,
  connection guard и параметры Xray-core, которые применимы к выбранному
  режиму.

Мастер первого запуска собирает сети, домены, сертификаты и обязательные
проверки. Редактируемые компактные строки открывают полные настройки в
модальном окне.

Панель не возвращает сохранённые UUID, private key, transport path/service
name или API secret в обычные формы. Поля секретов поддерживают только замену.
Полный клиентский профиль и URL подписки выдаются только явным действием
«скачать/получить ссылку», потому что без них клиент нельзя настроить.
Клиентские правила не расширяют права пользователя: настройка **Доступ к LAN**
всегда повторно проверяется серверным Xray.

Для каждого включённого удалённого пользователя `client_tun_address` задаётся
в Web UI отдельно. Это должен быть свободный IPv4 host/CIDR с пригодным адресом
и префиксом `/30` или шире, не пересекающийся с LAN, Wi‑Fi, VPN и другими
сетями устройства клиента. Значение из примера или runtime fallback не
подставляется: без явно сохранённого адреса Validate и экспорт профиля
завершаются ошибкой.

## Безопасные значения по умолчанию

- `system.deployment_ready: false` блокирует применение поставляемого примера.
- Пользователи, локальные клиенты и подписка в `config/` выключены.
- HTTPUpgrade и прямой Reality-вход выключены.
- IPv6 блокируется только для управляемых клиентов (`block_managed`), а не во
  всей сети.
- Удалённые VLESS-профили получают dual-stack TUN. Их публичный IPv6 идёт
  только через назначенный VLESS-лист (`remote_ipv6_mode: proxy_only`); при
  IPv4-only WAN прямой выход IPv6 не используется.
- Control API и Xray gRPC API слушают только loopback контейнера.
- Management UI разрешён только management CIDR и не публикуется через
  Cloudflare.
- RouterOS management закрыт для удалённых VLESS-пользователей.
- Origin 443 принимает только официальные сети Cloudflare.
- Удалённый публичный трафик блокируется, если все узлы назначенной
  VPN-политики недоступны.

## Файлы конфигурации

| Файл | Назначение |
|---|---|
| `config/gateway.yaml` | безопасный незаполненный reference-seed контракта |
| `config/networks.yaml` | пустой split-reference без активных примерных CIDR |
| `config/users.yaml` | удалённые пользователи и профили доступа к LAN без UUID |
| `config/policies.yaml` | страны, failover, сервисы и порядок route rules |
| `config/subscriptions.yaml` | провайдеры без URL/токенов |
| `config/rulesets.yaml` | локальные rule sets и правила обновления |
| `secrets/` | runtime-секреты с правами 0600, не для Git |
| `client-exports/` | чувствительные клиентские профили, не для Git |

`gateway.example.yaml` — полный обзор контракта для аудита. Файлы `config/*.yaml`
— безопасные reference-seeds без активных примерных сетей; Web UI хранит
черновик и поколения в state repository и публикует runtime-файлы через staging
и атомарную замену. Ручное редактирование допустимо только при восстановлении.

## Проверки проекта

На Linux-хосте разработчика:

```sh
make validate
make test
make ui-check
make image-bundle
```

На Windows тот же release bundle собирается командой
`.\scripts\build-routeros-bundle.ps1`. Нужен Docker или Podman. Упаковщик
проверяет внутренний Docker manifest, ровно один `linux/arm64` image,
application version и создаёт versioned tar, `.sha256`, manifest и копию
RouterOS-скриптов атомарно. ZIP, `docker export`, multi-platform и
произвольный OCI archive не принимаются.

В контейнере preflight обязательно проверяет Xray и Nginx:

```sh
xray run -test -config /config/generated/xray.json
nginx -t
```

`make update CONFIRM=RECOVERY` и `make rollback CONFIRM=RECOVERY` оставлены
только для аварийного восстановления. Обычный администратор выполняет check,
Apply, backup, обновление и откат кнопками Web UI.

Обновление контейнера через Web UI принимает только один `.tar`; созданный для
maintainer bundle файл `.sha256` в форму обновления не загружается. Полное
удаление и обновление подтверждаются действующей сессией и одной галочкой без
повторного ввода пароля. Пароль запрашивается при восстановлении `.sbgw`, так
как он нужен для расшифровки архива.

## Ограничения

- Доступ VLESS-клиента к LAN — TCP/UDP-проксирование, а не Ethernet bridge.
  Broadcast, multicast, mDNS и автообнаружение могут не работать.
- Внутреннее устройство обычно видит IP контейнера, а не удалённого телефона.
- HTTPUpgrade нельзя считать поддержанным конкретным CDN до реального smoke
  test.
- Пропускную способность конкретного MikroTik нельзя гарантировать по
  спецификации процессора или результатам CHR.
  Испытание 10×1080p, температура, packet loss и устойчивость требуют
  физического роутера, реального канала и VPS.
- Репозиторий позволяет выполнить статические и контейнерные проверки, но не
  заменяет hardware/end-to-end приёмку MikroTik и Cloudflare.
