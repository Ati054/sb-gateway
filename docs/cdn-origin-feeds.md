# Автообновление адресов CDN origin

**Защита origin → Официальные CIDR · авто** использует только опубликованные
провайдером адреса серверов, обращающихся к origin. Доступно для WS, gRPC,
HTTPUpgrade, XHTTP и отдельного CDN-входа подписки. Подписка на готовом
CDN-развёртывании наследует его защиту.

## Источники

| CDN | Официальный источник | Обновление |
|---|---|---|
| Cloudflare | [IPv4](https://www.cloudflare.com/ips-v4), [IPv6](https://www.cloudflare.com/ips-v6) | Ежедневно; смешанный origin-порт — control plane IPv4 каждые 15 минут |
| Gcore | [public-net-list](https://api.gcore.com/cdn/public-net-list) | Control plane, каждые 15 минут |
| EdgeCenter | [public_net_list](https://api.edgecenter.ru/cdn/public_net_list) | Control plane, каждые 15 минут |
| Yandex | [CDN prefixes](https://tech.cdn.yandex.net/prefixes/yc.json) | Control plane, каждые 15 минут |
| Beeline | [ip2origin](https://api-cdn.beelinecloud.ru/app/nodes/v2/ip2origin/?with_extra_zones=true) | Control plane, каждые 15 минут |
| Timeweb | [ip2origin](https://cdn-api.timeweb.cloud/app/nodes/v2/ip2origin/?with_extra_zones=true) | Control plane, каждые 15 минут |
| CDNetworks, VK Cloud, другой CDN | Универсальный публичный origin feed для нашего сценария не подтверждён | Секретный заголовок или ручные IPv4 CIDR |

Beeline/Timeweb: используется **ip2origin**, не **ip2user**, с дополнительными
зонами (`with_extra_zones=true`). Принимаются документированный `Completed` и
реальный `OK`. У EdgeCenter путь содержит подчёркивания. Устаревший хост
Beeline `api.cdn.beeline.ru` заменён актуальным из
[OpenAPI](https://doc-cdn.beelinecloud.ru/api_desc/openapi/cdn-node-list-api-v2.yaml).
Форматы сверены с [OpenAPI Timeweb](https://cdn-doc.timeweb.cloud/api_desc/openapi/cdn-node-list-api-v2.yaml)
и [OpenAPI EdgeCenter](https://api.edgecenter.ru/cdn/docs/openapi.yaml).

Feeds публичные и не требуют платной опции/токена. Это **не** означает наличия
постоянного Free-тарифа у каждого CDN. CDNetworks Origin Shield зависит от
продукта, включения shield и его локации; его API нельзя считать универсальным
списком CDNetworks. ASN, DNS домена и адреса серверов раздачи не подставляются.

## Безопасность и применение

- Cloudflare сохраняет прежний независимый RouterOS updater. Новые адаптеры
  управляют отдельными `SB_CDN_<PROVIDER>_V4`, не меняя старые Cloudflare-списки.
  Для смешанных origin-портов используется отдельный `SB_CDN_CLOUDFLARE_V4`.
- Фиксированные HTTPS URL, проверка сертификата, без редиректов, системного
  proxy, пользовательских URL и секретов CDN.
- Максимум 1 МиБ; проверяются JSON, статус, все CIDR и число записей.
  Пустой/повреждённый ответ, частные/служебные и чрезмерно широкие сети отклоняют
  весь ответ. IPv6 проверяется, но новые списки используются только существующим
  IPv4 public ingress: IPv6-доступ этим не включается.
- Первый Apply требует корректный список в health-фазе транзакции; иначе новый
  candidate не принимается. Проверенный снимок сохраняется в auxiliary state
  `cdn-feeds.json`, переживает перезапуск и повторно используется свежим при Apply.
  Статические адреса RouterOS сохраняются при остановке контейнера/перезагрузке.
- Фоновые обновления относятся только к активным входам, сериализованы с
  Apply/rollback, не перезапускают Xray и не очищают conntrack. На смешанных
  origin-портах изменившийся CIDR-файл вызывает graceful reload Nginx. Один проход
  обновляет один CDN, отдавая очередь дольше всего ожидающему источнику: сбои
  одного провайдера не блокируют остальные. После ошибки повтор через минуту;
  между проходами 15 секунд. Повторное использование свежего снимка при Apply
  не переносит время следующего фонового запроса.
- Сначала добавляются новые адреса пакетами, затем чтением RouterOS проверяется
  весь новый состав, и лишь затем удаляются устаревшие собственные записи.
  При прерывании подготовки остаются старые адреса и уже добавленные проверенные
  новые; следующий проход завершает синхронизацию. Это не атомарная замена всего
  списка, но пустого промежуточного списка нет.
- Сбой загрузки не меняет LKG. Apply может использовать сохранённый проверенный
  LKG; без него вход не открывается всем. Ошибка записи в RouterOS не фиксирует
  новый снимок как успешный. Чужие, отключённые, динамические или дублирующиеся
  записи в управляемом списке блокируют синхронизацию; чужие списки не изменяются.
- NAT/filter ограничены списком своего провайдера. Его адреса исключены из
  клиентского scanner-quarantine: один CDN IP обслуживает многих клиентов.
  Разные source-границы на одном origin-порту поддерживаются через отдельные
  проверки Nginx по origin-доменам; см. [Общий TCP ingress](shared-tcp-ingress.md).
- Secret-header/manual-cidr настройки автоматически не мигрируют. CIDR не
  удостоверяет конкретный аккаунт CDN и не заменяет mTLS или секретный заголовок.

## Диагностика и проверка

Авторизованный `GET /api/v1/status` содержит `cdn_feeds`: `state` (`ok`, `stale`,
`failed`), `last_attempt_at`, `last_success_at`, `ipv4_count`. Это последние
сохранённые результаты, включая ранее использованные CDN; текущий набор
определяется включёнными входами. CIDR в status не передаются. Аудит:
`cdn-feeds.refresh`, журнал: `cdn-feeds`.

Тесты проверяют parser всех адаптеров, повреждённые ответы, LKG после повторного
открытия repository, первый Apply без feed, ошибки RouterOS, подготовку 405
адресов, отсутствие удаления после тихой ошибки скрипта, source-границы и
выключенные входы. RouterOS-регрессия отдельно запрещает имя переменной цикла,
совпадающее с полем `address`: на RouterOS 7.21.5 такое совпадение заставляло
все элементы после первого повторно находить первую строку. Общий исправленный
путь покрыт для Cloudflare, Gcore, EdgeCenter, Yandex, Beeline и Timeweb.
Обычные тесты не обращаются к CDN.

Опционально: `SB_TEST_LIVE_CDN_FEEDS=1 go test ./internal/cdnfeed -run
TestLiveOfficialFeeds -v -count=1`. 2026-09-09 реальные ответы всех источников
прошли Go parser: Cloudflare 15 IPv4 сетей, Gcore 357, EdgeCenter 78, Yandex 99,
Beeline 208, Timeweb 208. Исправленный пакетный цикл дополнительно проверен на
RouterOS 7.21.5: три тестовые сети созданы и удалены полностью. Это проверка
feed и механизма записи, **не** испытание CDN-трафика.

HTTP-загрузка каждого официального feed ограничена 45 секундами. Запись и
последующее чтение полного RouterOS address-list выполняются отдельным
ограниченным этапом до двух минут; поэтому первый Apply большого списка не
теряет остаток времени на сетевой загрузке. Общий Apply остаётся ограничен
пятью минутами и сохраняет автоматический откат.

Проверка UI: изолированный React fixture из действующих JSX-полей и CSS,
Chrome 1440/390 px, все девять вариантов CDN, переключение методов защиты,
фокус с клавиатуры, отсутствие горизонтального переполнения. Это не прогон
полной панели на роутере. Выполнены профильные Go-тесты, `go vet`, TypeScript
и Node-тесты соответствия UI реестру backend.

При первоначальной проверке общий Windows `go test -p 1 ./...` остановился в
`internal/rulesets/TestRefreshFailureKeepsLastKnownGood`: Windows не смог удалить
временный каталог при cleanup (`The directory is not empty`). Последующий
общий Linux-прогон `go test ./cmd/... ./internal/... ./routeros/...` и `go vet`
прошли при проверке shared ingress; испытание на реальном роутере остаётся отдельным.
