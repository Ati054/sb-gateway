# TLS-сертификаты

## Локальный CA для TLS Pin

В **Подключения → TLS-профили** режим **Локальный CA · TLS Pin** принимает один
конкретный DNS SNI и при первом сохранении создаёт ECDSA P-256 `MyRootCA` на
20 лет и подписанный им leaf на 10 лет. DNS API, подтверждение владения доменом,
публичный CA и Certificate Transparency не используются. Режим предназначен
для клиентов, которые получают pin leaf из подписки; системное доверие к Root CA
на клиенте не требуется.

Обычное сохранение не меняет ключи. Изменение SNI или действие **Пересоздать
сертификат** создаёт новую Root/leaf-пару и новый pin; после этого клиент должен
обновить подписку. Старый и новый pin одновременно не выдаются.

Root-сертификат, Root-ключ, leaf-цепочка и leaf-ключ хранятся в SecretStore.
Зашифрованный `.sbtls` переносит полный локальный CA, а API не возвращает его
приватные ключи. Частный CA не гарантирует прохождение сетевого белого списка:
SNI остаётся видимым в ClientHello, а правила сети проверяются отдельно.

## Автоматические сертификаты ACME

В **Подключения → TLS-профили → Настроить** режим **Автоматически · ACME**
выпускает и продлевает сертификат Let’s Encrypt через DNS-01. Ручная загрузка
PEM остаётся доступной. Требуется новый образ с `/usr/local/bin/sb-acme`:
обновления только панели или основного бинарника недостаточно.

## Настройка

1. Укажите имя профиля, домены сертификата и email для ACME. Допускается до
   десяти имён; международные имена задаются в punycode, wildcard — `*.example.com`.
2. Выберите **провайдера авторитетных DNS-записей**, а не регистратора или CDN
   по названию тарифа. Доступны REG.RU (логин/пароль API), Gcore DNS и
   Cloudflare DNS (API-токен), Yandex Cloud DNS (ID каталога и JSON авторизованного
   ключа сервисного аккаунта). Наличие CDN Free само по себе не подтверждает
   наличие DNS API или нужных прав в аккаунте. Для остальных DNS-провайдеров
   доступен **ACME-DNS · другой провайдер**, описанный ниже.
3. Дайте доступ к TXT-записям только нужной зоны, насколько это позволяет
   провайдер. Для Cloudflare нужны DNS Edit и Zone Read соответствующей зоны.
   Если API ограничен по исходному IP, разрешите фактический исходящий адрес
   контейнера. Родительский домен переносить не требуется.
4. Примите условия Let’s Encrypt и нажмите **Выпустить сертификат**.
   **Сохранить изменения** сохраняет настройки, но само по себе не запускает
   первый выпуск. Имена публичных сертификатов попадают в Certificate Transparency.
5. Дождитесь подтверждения выпуска, назначьте TLS-профиль нужным подключениям
   и выполните Apply. Первое подключение пары меняет draft; последующие
   продления уже используемой пары не требуют Apply и не меняют RouterOS.

Проверка использует временные TXT `_acme-challenge`, не меняет A/AAAA/CNAME
пользовательских сервисов и не требует входящих портов 80/443. Нужны исходящие
HTTPS к CA/DNS API и DNS-запросы, включая проверку авторитетных серверов.
Для recursive DNS worker создаёт на время задачи отдельный loopback-resolver
без cache и направляет его на выбранный профиль `dns.direct_resolver`. Поэтому
отрицательный ответ, ранее закэшированный RouterOS до появления TXT, не
переиспользуется. Это не отменяет отрицательный cache выбранного публичного
recursive DNS или задержку публикации на авторитетных NS. DoH или DoT выбранного
профиля сохраняется с обычной TLS-проверкой;
DoH использует тот же DoT fallback того же провайдера, что и основной DNS-путь,
а не скрытое понижение до UDP. Lego по-прежнему требует видимость TXT через
recursive resolver **и** все авторитетные NS. Для уже применённой системы ACME
берёт applied direct-профиль, а не несохранённые правки draft; до первого Apply
используется draft. Неподдерживаемый профиль останавливает выпуск, не возвращаясь
к локальному resolver. Для первого сертификата после исправления нужен явный
ручной повтор; уже установленная управляемая пара остаётся в контуре
автопродления.

### Время ожидания DNS-01

Worker опрашивает DNS раз в 10 секунд, но не отменяет строгую recursive и
authoritative проверку. Автоматический предел ожидания временной TXT: **4 ч
15 мин** у REG.RU и ACME-DNS, **90 мин** у Cloudflare DNS, Yandex Cloud DNS и
Gcore DNS. TXT, подтверждённый раньше, продолжает выпуск сразу: это максимальные
стандартные пределы, а не обязательная пауза. Они не гарантируют custom SOA/TTL
или сеть CA: фактическая отрицательная запись public resolver может жить дольше.
Основание выбора — опубликованные параметры зон и TTL: [REG.RU](https://help.reg.ru/support/dns-servery-i-nastroyka-zony/nastroyka-resursnykh-zapisey-dns/nastroyka-resursnykh-zapisey-v-lichnom-kabinete),
[Cloudflare DNS](https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/),
[Yandex Cloud DNS](https://yandex.cloud/en/docs/dns/concepts/resource-record)
и [Gcore DNS](https://gcore.com/learning/what-is-dns-ttl).

Для **ACME-DNS · другой провайдер** поле **Ожидание DNS** можно переключить на
**Вручную** и указать целое число от 1 до 1440 минут. Значение **Автоматически**
не передаёт override и оставляет 4 ч 15 мин; при выборе ручного режима форма
начинает с эквивалентных 255 минут. У прямых DNS-провайдеров ручной override не
доступен и backend его отклоняет.

Полный deadline одноразового worker — DNS-бюджет, ещё 5 минут на setup/order и
до 10 минут на каждое из максимум десяти SAN; control plane оставляет ещё минуту
на результат и локальную установку. Это один общий лимит на order, а не умножение
DNS-ожидания на SAN. В панели одновременно работает только один ACME job, поэтому
долгая проверка может задержать выпуск или продление другого TLS-профиля.

Пока задача выполняется, панель показывает время её начала и этот общий предел
ожидания. Это не прогноз времени завершения. Новый worker также может передать
последнюю достигнутую контрольную точку: подготовку, регистрацию CA, создание
DNS-записи, проверку DNS и подтверждение домена, запрос сертификата или его
локальную установку. Это best-effort сигнал, а не непрерывный журнал и не точное
состояние каждого SAN: после DNS callback CA всё ещё может завершать order.
Старый worker либо отсутствующий сигнал оставляет обычную общую надпись. Сигнал
содержит только allowlisted этап, живёт лишь во время текущей задачи и не меняет
сам выпуск. Если обновить статус не удалось, последняя надпись о выполняющейся
задаче скрывается; кнопка выпуска остаётся заблокированной по последнему безопасно
известному состоянию.

При неудаче worker передаёт панели только версионированный ограниченный набор полей:
стадию до DNS-проверки, ожидание TXT или после DNS-проверки; фиксированную категорию
CA/сети; для известных
ответов CA — короткий тип проблемы и HTTP-статус. Точный ответ DNS API или CA не
выводится, поскольку он может содержать учётные данные, URL, доменные имена или тело
ответа. До запуска worker отключает как стандартные, так и независимые логи lego:
stdout остаётся одним JSON-ответом и не смешивается с upstream логами. Старый worker
без такого envelope остаётся совместимым: панель показывает
безопасную причину по его коду завершения.

Если типизированный ответ lego о лимите CA содержит положительный `Retry-After`,
панель сохраняет этот срок и не принимает ручной повтор до его истечения.
Сохранение или отключение/включение профиля разрешено, но не сбрасывает этот срок.
Непредставимое внутреннее значение блокирует
повтор fail-closed. Это относится только к положительному `Retry-After`, доступному
в типизированном ответе lego: worker не разбирает сырой заголовок или текст ошибки,
поэтому не обещает обработать все ответы CA (включая 503). См. также
[ограничения Let's Encrypt](https://letsencrypt.org/docs/rate-limits/).

Первый выпуск всегда ставит в очередь только кнопка **Выпустить сертификат**.
После неудачи он не создаёт новый order сам — в том числе после перезапуска,
сохранения настроек, отключения/включения профиля или истечения старого
`next_attempt`. Статус предлагает короткий ручной повтор не раньше чем через
5 секунд от начала предыдущей попытки и, при наличии, после срока CA. Это не
отменяет ограничение CA. Автоматика относится только к продлению: она требует
сохранённую управляемую PEM-пару, совпадающие metadata и SAN; повреждённая или
отсутствующая пара переводит выпуск в ручной режим. После неудачного продления
такой подтверждённой пары следующий автоматический запуск остаётся через 15
минут после завершения задачи.

У уже установленной подходящей пары кнопка **Выпустить сертификат** не
показывается до начала окна продления. Подходящая означает, что панель заново
проверила управляемый bundle, ключ, metadata и текущий набор SAN; сертификат
уже действует, а окно начинается в последней трети его фактического срока, но
не раньше чем за 30 дней до окончания. Изменение доменов, отсутствие или
повреждение пары, ещё не начавшийся либо истёкший срок оставляют ручный путь
для восстановления или выпуска. Сервер повторяет проверку до сохранения
учётных данных и постановки order в очередь: устаревшая вкладка не может
создать лишний выпуск. Перестановка SAN, регистр букв и завершающая точка не
считаются изменением доменов в интерфейсе. Это снижает лишние production
orders, но не отменяет внешние лимиты CA.

Если CA успел создать сертификат при **первом выпуске**, а локальная установка
результата не подтвердилась, панель не создаёт второй order автоматически.
Восстановление такого результата и ACME renewal information — отдельная будущая
задача; до неё оператор видит безопасный статус и действует вручную с учётом CA
hold. Это не меняет действующий автоматический повтор неудачного продления
подтверждённой уже установленной пары.
У прямых DNS-адаптеров записи удаляются после проверки; при принудительном завершении процесса
оставшийся challenge TXT может потребовать очистки. Lego поддерживает CNAME
делегирование challenge в отдельную управляемую DNS-зону; оно настраивается
пользователем, в панели пока не создаётся и отдельно на реальном DNS не проверено.

## Yandex Cloud DNS и другие DNS-провайдеры

Для Yandex нужен **авторизованный ключ сервисного аккаунта** (`key.json`),
не временный IAM access token. Панель принимает файл до 16 КиБ и ID каталога,
хранит их в SecretStore и передаёт worker через закрытый pipe. Worker использует
адаптер lego `yandexcloud`; SDK и обновление IAM-токена загружаются только на
время выпуска/продления, не в постоянно работающую панель. Сервисному аккаунту
нужны права DNS API (см. [адаптер lego](https://go-acme.github.io/lego/dns/yandexcloud/));
ограничьте каталог/зоны предназначенными для ACME. Реальный выпуск через аккаунт
Yandex ещё не проверен: автоматические тесты проверяют валидацию ключа и создание
адаптера без сети. Поддержка Yandex CDN в транспортах — отдельная функция; наличие
CDN не переносит DNS-зону автоматически и не гарантирует бесплатность DNS API.

Покупка домена у другого регистратора не требует другого ACME-адаптера, если
авторитетный DNS обслуживает один из поддерживаемых провайдеров. Для иных API
можно делегировать `_acme-challenge` CNAME в поддерживаемую зону. Произвольные
скрипты/HTTP-шаблоны провайдеров из панели не исполняются: у DNS API разные
аутентификация, поиск зоны, добавление и безопасное удаление TXT. Универсальный
webhook не поддерживается. Дополнительный адаптер ACME-DNS использует фиксированный
контракт `/update`, а не произвольный HTTP-шаблон.

### ACME-DNS для неподдерживаемого DNS API

Режим ACME-DNS использует отдельный DNS lane, ручной повтор, ограниченные стадии
диагностики и типизированный `Retry-After` CA. Worker возвращает панели только
JSON-ответ и не передаёт журналы lego.

Нужен отдельный доверенный [ACME-DNS-сервис](https://github.com/acme-dns/acme-dns)
с публичным DNS и HTTPS API. Это не название регистратора и не встроенный DNS-сервер
контейнера. Можно использовать свой сервис или сервис доверенного оператора;
панель не выбирает публичный сервис и не регистрируется в нём автоматически.
Оператор сервиса способен подтверждать выпуск сертификатов для делегированных имён.

1. Получите у сервиса JSON учётной записи (`POST /register` по его инструкции).
   Нужны `username`, `password`, `subdomain`, `fulldomain`. При ограничении `allowfrom`
   разрешите фактический исходящий IP контейнера. Панель это ограничение не меняет.
2. В TLS-профиле выберите **ACME-DNS · другой провайдер**, задайте HTTPS-адрес API
   и загрузите JSON (до 20 КиБ). Для одного базового имени подходит ответ `/register`
   без изменений; дополнительные поля регистрации, включая `allowfrom`, не сохраняются.
3. У текущего DNS-провайдера один раз добавьте показанную CNAME-запись:
   `_acme-challenge.api.example.com` → `идентификатор.auth.example.net`.
   A/AAAA/CNAME самого `api.example.com`, NS основного домена и записи других
   поддоменов менять не нужно. На имени challenge не должно оставаться конфликтующей TXT.
4. Нажмите **Проверить CNAME**. Это проверка DNS, не проверка ключа API и не выпуск
   сертификата. Затем примите условия CA и нажмите **Выпустить сертификат**.
   Доступ к `/update` проверяется при настоящем выпуске.

Каждому различному базовому имени нужна отдельная регистрация/`fulldomain`.
`api.example.com` и `*.api.example.com` используют одну запись: ACME-DNS хранит
два чередующихся TXT-значения для одновременных challenge. Для нескольких имён
загрузите один JSON следующего вида (значения ниже — только пример):

```json
{
  "api.example.com": {
    "username": "user-api", "password": "replace-with-service-key",
    "subdomain": "record-api", "fulldomain": "record-api.auth.example.net"
  },
  "msk.example.com": {
    "username": "user-msk", "password": "replace-with-another-service-key",
    "subdomain": "record-msk", "fulldomain": "record-msk.auth.example.net"
  }
}
```

JSON должен точно покрывать базовые имена профиля; ключи `*.` в нём не нужны.
Не используйте одну регистрацию для разных базовых имён или независимых
одновременно работающих выпускателей. После переноса выключите продление на старом шлюзе.

Перед каждым выпуском/продлением worker проверяет все CNAME **до обращения к CA**,
а перед обновлением TXT — соответствующую запись ещё раз. И CNAME, и обычная
проверка распространения TXT средствами lego используют один свежий direct DNS
lane; успешная проверка не гарантирует видимость из сети CA. При ошибке старый
сертификат сохраняется. Неудачный первый выпуск требует явного повторного нажатия
**Выпустить сертификат** через 5 секунд после начала неудачной попытки; подтверждённая
уже установленная пара продлевается автоматически и после неудачи повторяется через
15 минут **после завершения** задачи. Ручной Apply для продления уже подключённой пары не нужен.

URL API допускает HTTPS и необязательный префикс пути/порт, без пароля, query
и fragment. TLS проверяется штатно; redirect, proxy из окружения, IP-литералы,
локальные/частные/служебные адреса и небезопасные смешанные DNS-ответы запрещены.
Соединение идёт на уже проверенный числовой IP без повторного DNS-разрешения.
Таймаут API — 30 секунд, ответ — до 4 КиБ. При смене URL нужно загрузить
учётные записи заново: сохранённые ключи не отправляются на другой сервис.

У ACME-DNS нет API удаления TXT: после проверки остаются последние challenge
значения, а постоянный CNAME сохраняется для продления. Это не пароль API.
Адрес сервиса, регистрации и ключ ACME-аккаунта входят в зашифрованный `.sbtls`;
импорт, как и у других провайдеров, не включает продление самостоятельно.

Проверки реализации покрывают протокол `/update`, DNS-01 payload, изоляцию
SAN/wildcard, защиту адресов и redirect, сессию/CSRF, отсутствие ключей в
статусе, сохранение пары при ошибке, таймер продления и зашифрованный перенос.

Для одновременных тестов Gcore и Yandex CDN используйте отдельные клиентские
имена, например `gcore.example.com` и `yandex.example.com`. Обычный CNAME одного
имени указывает на один CDN; общий origin и его TLS-профиль могут использоваться
обоими при совпадении настроек origin SNI. Multi-CDN под одним клиентским именем
требует отдельного управления DNS/трафиком. [Yandex: настройка ресурса](https://yandex.cloud/en/docs/cdn/operations/resources/create-resource).

## Перенос отдельного TLS-профиля

В **Подключения → TLS-профили → Настроить** действие **Экспорт** между удалением
и отменой у сохранённого профиля с TLS-парой
создаёт файл `.sbtls`. Задайте пароль от 12 символов и храните его отдельно.
Архив содержит сертификат с цепочкой, приватный ключ, для управляемой ACME-пары —
настройки, DNS-доступ и имеющийся ключ ACME-аккаунта, а для локального CA — его
сертификат и приватный ключ. Незавершённый выпуск нужно
сначала дождаться. Профиль без готовой TLS-пары экспортировать нельзя.

На другом шлюзе нажмите **Импорт**, выберите файл и введите пароль. Создаётся
**новый выключенный профиль с новым ID**; существующие профили, назначения,
маршруты и RouterOS не меняются. ID кодируется в hex: любой случайный токен
соответствует схеме идентификаторов. Очередь выпуска, попытки и ошибки исходного
шлюза не переносятся. Даже если сертификат истёк, его можно восстановить в
выключенный профиль и затем явно настроить выпуск; импорт не подтверждает
текущую доверенность или доступность сертификата извне.

После импорта:

1. Откройте новый профиль, проверьте домены, сертификат и DNS-доступ.
2. Для ACME выберите **Автоматически · ACME** и включите автопродление.
   Если API ограничен по IP, разрешите исходящий адрес нового шлюза.
3. Включите профиль, сохраните, назначьте его нужным подключениям и выполните Apply.
4. После проверки боевого шлюза отключите автопродление на тестовом:
   экспорт сам по себе не отключает исходный профиль.

Полный recovery backup для переноса сертификата не нужен. Тестовые firewall
правила, маршруты, пользователи и остальные секреты в `.sbtls` не входят.
При потере ответа импорта сначала обновите список: повторный импорт создаёт
ещё один профиль и не заменяет предыдущий.

Формат `SB-TLS-1`: AES-256-GCM, случайные salt/nonce, scrypt (N=32768, r=8, p=1;
около 32 МиБ рабочей памяти). Только одна операция переноса выполняется
одновременно; параметры KDF фиксированы, размер содержимого ограничен 1 МиБ.
Архив не привязан к паролю администратора или аппаратному ключу роутера.
Забытый пароль архива восстановить нельзя. Передавайте файл доверенным способом:
пароль шифрует содержимое, но не доказывает личность отправителя.

Проверки покрывают шифрование, повреждение файла, сессию/CSRF, перенос ручной,
ACME- и local-CA-пары между отдельными хранилищами, сохранение чужой
конфигурации и продление после повторного открытия состояния.

## Пример с двумя поддоменами

Это пример, имена и адреса не зашиты в приложение:

| Имя | DNS | Назначение |
| --- | --- | --- |
| `api.example.com` | A/AAAA на публичный origin | Hysteria2 UDP 443; HTTPS origin TCP 443 |
| `msk.example.com` | CNAME на CDN | HTTPS-подписка клиентов |

Для CDN задайте origin `api.example.com`, HTTPS, origin SNI/проверку сертификата
по `api.example.com` и согласованный Host. CDN обслуживает собственный edge
сертификат `msk.example.com`; панель продлевает **origin** сертификат
`api.example.com`. Не нужно копировать приватный ключ edge на MikroTik.
Обновление edge остаётся ответственностью CDN. HTTPS-подписка не должна
кешироваться CDN; конкретный ресурс, Host/SNI, защиту origin и тариф проверяют
отдельно. Hysteria2 идёт напрямую по UDP, не через обычный HTTP CDN.
Одинаковый номер TCP/UDP-порта не создаёт между ними конфликта.

## Продление и отказы

- Настройки, аккаунт ACME, очередь и время повторной попытки сохраняются на SSD
  и переживают перезапуск контейнера. Работы выполняются последовательно.
- Продление начинается в последней трети фактического срока сертификата
  (не раньше чем за 30 дней). Срок 90 дней не предполагается неизменным.
- Ошибка выпуска не заменяет старую пару. Проверяются ключ, доверенная цепочка,
  SAN и оставшийся срок. Действующие SAN нельзя убрать из активной пары:
  для такого переноса создайте другой профиль.
- Сертификат и ключ заменяются одним атомарным PEM-файлом. Nginx проходит
  `-t` и graceful reload; при ошибке предпринимается восстановление предыдущего
  файла и reload. Не подтверждённая установка отображается ошибкой, а не успехом.
- Xray использует встроенное перечитывание файлов сертификата — до одного
  часа в закреплённой версии. Его соединения ради продления не перезапускаются.
  «Выпущен» подтверждает установку файла, а не внешний handshake каждого клиента.
- Неудачный **первый выпуск** не повторяется автоматически: после короткой
  паузы его можно поставить в очередь только явным ручным действием. Неудачное
  продление подтверждённой управляемой пары повторяется автоматически через 15
  минут. Пока задача queued/running, повторный клик отклоняется. Положительный
  `Retry-After` от CA имеет приоритет над коротким ручным ожиданием; после
  успеха ручной повтор ограничен часом. Квоты CA продолжают действовать; не
  используйте production выпуск как многократно повторяемый тест.
- Закрытие формы не отменяет очередь. Отключение автопродления или изменение
  настроек во время выпуска делает полученный старой задачей результат неприменимым.
  Старые файлы и DNS-доступ сохраняются для повторного включения/восстановления.

## Ресурсы и секреты

Lego 5.4.1 собран в отдельный worker с четырьмя штатными DNS-адаптерами и компактным
ACME-DNS-адаптером без дополнительного SDK. Worker не работает
постоянно: максимум одна задача, `GOMAXPROCS=1`, `GOMEMLIMIT=48MiB`, окно процесса
ограничено общим [deadline DNS-проверки и выпуска](#время-ожидания-dns-01).
Это **мягкий лимит Go**, не гарантия пикового RSS или CPU на hAP ax³.
Размер бинарника не равен его рабочей памяти. Общий лимит памяти
контейнера не повышается автоматически; пиковое потребление измеряется на стенде.

DNS-доступ и account key находятся в `/config/secrets/acme/<id>/`, управляемая
пара — `tls-profiles/<id>/acme-bundle.pem`. Файлы 0600, директории 0700;
SecretStore не шифрует их на диске. Защищайте SSD и резервные копии. Данные
передаются worker через stdin, не через аргументы или журнал. Статус API
не возвращает токен/ключи. Запись настроек требует сессию и CSRF. Зашифрованный
recovery archive включает эти секреты и `acme.json` вместе с остальным состоянием.

## Проверено / осталось проверить

Автотесты: валидация ввода, сессия/CSRF, первый выпуск только по кнопке,
сохранение пары при отказах, ручной retry после failed с коротким persisted
cooldown, автоматический 15-минутный backoff, защита queued/running,
сохранение/перезапуск и совместимость старых записей, отмена устаревшей задачи,
сохранение асинхронно выданной пары при редактировании профиля,
проверка цепочки/SAN и rollback Nginx. Для ACME recursive lane покрыты stale
NXDOMAIN против свежего TXT, отсутствие cache, UDP truncation/TCP, DoH/DoT с
проверкой TLS, отмена/лимиты и выбор active direct-профиля вместо draft.
2026-09-08 на тестовом CHR подтверждена причина прежнего сбоя: локальный
negative DNS cache мог пережить появление challenge TXT; реальный выпуск CA
этими unit-тестами не выполняется. Проверены Go test/vet, TypeScript,
контракты UI и форма в Chrome 1440/390 px с синтетическим API.
В одноразовом Linux-контейнере проверен настоящий Nginx: загрузка общего
PEM-файла, атомарная замена, graceful reload и новый TLS handshake с проверкой
доверия к новой паре. Тест: `SB_ACME_LIVE_NGINX=1 go test
./internal/controlplane -run TestACMELiveNginxBundleReload -count=1`.

Работу выбранного CA, права DNS-аккаунта, end-to-end CDN и автопродление нужно
проверить с собственным доменом и ограниченным DNS API-доступом. Тестовые
сертификаты и токены в образ не включаются.
