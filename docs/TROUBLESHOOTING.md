# Диагностика

Документ соответствует текущей эксплуатационной модели SB Gateway 1.6.x.

Проверяйте состояние в разделе **Эксплуатация**. Для передачи разработчику
скачивайте обезличенный диагностический архив. Не публикуйте UUID, приватные
ключи, пути транспортов, service name, ссылку подписки и исходный export с
секретами.

## Apply остановился до изменения RouterOS на `/rest/export`

Если Apply вернул `apply_failed`, а локальный журнал содержит
`POST /rest/export: context deadline exceeded`, RouterOS не успел завершить
создание обязательного текстового export. Рабочая конфигурация при этом не
меняется. Export и зашифрованный binary backup относятся к долгим action-командам
и используют отдельный двухминутный бюджет; короткий 15-секундный REST timeout
остаётся только у inventory и health-запросов. После восстановления отклика
RouterOS Apply можно безопасно повторить.

## Панель недоступна

1. Подключитесь к management LAN или к разрешённому VPN-источнику.
2. Откройте `https://<IP-контейнера>:9443`. Публичный домен транспорта для
   управления не используется.
3. В WebFig проверьте состояние контейнера, veth, bridge и счётчик правила для
   TCP/9443.
4. При crash loop остановите контейнер. Клиенты с режимом fail-open перейдут на
   основной WAN; клиенты с fail-closed сохранят только разрешённый LAN.
5. Запустите управляемый rollback через панель или RouterOS recovery script.

Не открывайте TCP/9443 со стороны WAN.

## Контейнер работает, но health-check не проходит

Readiness требует исправной конфигурации Nginx и Xray. Проверьте:

- `/config/generated/xray.json` существует;
- файлы сертификатов и секретов доступны только владельцу;
- `xray run -test -config /config/generated/xray.json` завершается с кодом 0;
- `nginx -t` завершается с кодом 0;
- на SSD хватает места, а RouterOS показывает свободную RAM;
- время и NTP корректны;
- журнал `sb-gateway appliance` не содержит повторяющегося падения компонента.

После исчерпания restart budget контейнер остаётся доступным для диагностики,
но watchdog прекращает обновлять readiness lease. RouterOS переводит локальный
трафик в BYPASS. Не увеличивайте restart budget до определения причины.

Если в журнале перед рестартом указаны только `api_configured,api_ready`, а
процесс Xray, listeners, TPROXY, policy route и DNS исправны, это отказ control
plane, а не dataplane. Такой случай использует отдельный порог 24
последовательных ошибок. Переход между control-plane и dataplane ошибками
начинает новую серию: накопленные таймауты API не могут превратить
один глубокий probe в немедленный рестарт. Причины `core_process`,
`core_config`, `listener_*`, `tproxy_*`, `route_*` или `dns_*` по-прежнему
используют быстрый порог.

Строка **Количество перезапусков** на главной странице берёт значение из
RouterOS `restart-count` и показывает число автоматических перезапусков
текущего запуска контейнера. Новый запуск начинает отсчёт заново, поэтому
ненулевое значение сразу указывает на сбой после последнего запуска. Внутренняя
история watchdog по-прежнему хранит скользящее окно 60 минут для crash-loop
limiter. Последняя записанная watchdog-причина доступна в
`/state/watchdog-last-restart.json`; файл не содержит ключей или адресов.

Резкое снижение `memory-current`, совпавшее с увеличением `restart-count`, —
следствие перезапуска процессов, а не штатная очистка кеша. Проверьте
`memory.events`: ненулевые `oom`/`oom_kill` означают нехватку памяти; при нулях
ищите инициатора рестарта в журнале watchdog. Предупреждения Xray находятся в
`/logs/xray-error.log`, а вывод процесса и panic — в
`/logs/xray-process.log`. Последний ограничен 4 МиБ и хранит ещё две
ротированные копии. Поштучный access-log Xray отключён, чтобы потоковые
подключения не перегружали RouterOS и не вытесняли аварийную диагностику.
Плавные колебания Go heap и страничного кеша без изменения `restart-count`
допустимы.

Журналы доступны без shell в **Эксплуатация → Журналы SB Gateway**. Окно
показывает последние 300 строк, обновляется каждые три секунды и позволяет
скопировать видимый фрагмент. Большую область журнала можно свернуть стрелкой,
не закрывая окно и настройки уровня. API принимает только два фиксированных
источника Xray `error`/`process` и три системных источника
`system`/`nginx`/`lifecycle`; передать произвольный путь к файлу нельзя.
Control-plane журнал ограничен 4 МиБ и хранит одну предыдущую ротацию.

В том же окне выбирается `error`, `warning`, `info`, `debug` или `none`.
Настройка сначала сохраняется в черновик и меняет Xray только после общего
Apply. Значение по умолчанию — `warning`. Применённый `debug` автоматически
заменяется на `warning` через 15 минут с отдельным перезапуском Xray; таймер
хранится в состоянии control plane, не зависит от открытого браузера и не
продлевается повторным Apply несвязанных изменений.
Поштучный access-log соединений через эту настройку не включается.

Если выбор `.tar` сразу сообщает об отсутствии каталога проекта, укажите
**Настройки → Контейнер и хранилище → Каталог проекта на внешнем SSD**. Preflight
не начал загрузку, поэтому повторно выбирать архив безопасно. После нажатия
**Подготовить обновление** состояние отображается в отдельном окне с таймером;
временная недоступность панели во время переключения ожидаема. Если окно было
закрыто, обновите страницу: активная lifecycle-операция откроется снова.

Одиночный `timeout, tries 1/3` OCI healthcheck при неизменных `restart-count` и
PID Xray означает задержку control-plane probe, а не падение контейнера. В
актуальном образе API и HTTPS проверяются параллельно с семисекундным пределом;
три последовательных неуспеха по-прежнему считаются реальной неисправностью.
Для обрывов XHTTP именно во время многопоточного speed test проверьте клиентский
экспорт: рекомендуемые значения — `maxConnections=3`, `maxConcurrency=0`.
Это ограничивает рост числа Reality/TLS-соединений на мобильных сетях и
соответствует штатному профилю Xray-core 26.7.28. Значение
`maxConcurrency=1` не используйте как постоянный профиль: оно предназначено
для узкого сценария синтетического многопоточного теста и может вызывать
периодические обрывы у мобильных клиентов.

## Панель показывает «Требуется синхронизация»

Статус означает одно из двух:

- draft отличается от active-конфигурации;
- active-конфигурация сохранена, но runtime ещё не построен или не совпадает с
  active revision.

Откройте план изменений. Если draft и active совпадают, запустите безопасную
синхронизацию runtime. Панель не должна показывать этот статус после обычного
просмотра страницы. Повторное появление без изменения настроек указывает на
ошибку reconcile; сохраните operation ID и диагностический архив.

## У локального клиента нет интернета

| Проверка | Ожидаемое состояние |
|---|---|
| Watchdog | `HEALTHY` или `BYPASS` |
| Внутренний адрес | не получает policy mark SB Gateway |
| Новый публичный поток | виден на TPROXY либо уходит в main/WAN при BYPASS |
| IPv4 | работает независимо от политики IPv6 |
| DNS | UDP и TCP 53 следуют режиму маршрутного листа |

Закройте старые соединения после перехода в BYPASS. Conntrack сохраняет путь
уже установленного потока. Не отключайте группы mangle или firewall вручную.

## Исключения идут не через тот выход

Выбранные сервисные карточки меняют путь вместе с режимом листа:

- **VLESS + WAN**: основной трафик идёт через выбранную VPN-политику,
  отмеченные сервисы идут через WAN;
- **WAN + VLESS**: основной трафик идёт через WAN, отмеченные домены идут через
  выбранную VPN-политику;
- пустой список: весь публичный трафик следует основному выходу режима.

В актуальном Web UI новые исключения добавляются через доверенный каталог по
имени сервиса, домену или URL. Сырой список `direct_domains` оставлен только как
совместимое внутреннее поле старых конфигураций и при обычном редактировании не
обнуляется. Если сервис не найден, не вводите отдельные CDN-домены вручную:
сначала обновите или дополните доверенный service pack.

Проверьте `/config/rulesets/<id>.json` через штатный audit: активный пакет
должен содержать хотя бы одно поддерживаемое условие. Пустой ruleset теперь
останавливает Check/Apply с `no usable match conditions`, а не создаёт широкое
правило. Для вручную найденной карточки количество правил включает рекурсивные
`include`; нулевой результат каталог не принимает. Портовые карточки обязаны
оставаться ограниченными `network` и `port`/`port_range` и не менять DNS lane.

Если основной документ сайта отвечает, но приложение сообщает, что страница
не открывается, отдельно проверьте QUIC/UDP 443, TLS sniff и фактический
назначенный выход. HTTP `503` от самого origin подтверждает достижимость пути,
но не работоспособность сайта с IP выбранного выхода; это не следует лечить
расширением карточки до общего CDN.

Если document сначала показывает WAF/challenge или белую страницу, извлеките
конкретный challenge hostname и проверьте, что он присутствует в ruleset этой
же карточки и в её policy-DNS lane. Document и challenge должны видеть один
egress IP. Добавляйте только узкий suffix поставщика challenge: например,
карточка `binance` включает `token.awswaf.com`, но не весь CloudFront/AWS.

Пакеты `direct_services` служат отдельными фиксированными WAN-исключениями.
Проверьте их перед поиском ошибки в `direct_domains`. Общий CDN целиком может
перехватить посторонние сайты, поэтому добавляйте домены конкретного сервиса.

## DNS утекает мимо выбранного маршрута

Проверьте UDP и TCP 53. Оба протокола должны попасть в управляемый DNS-путь и
вернуться через выход маршрутного листа. Затем проверьте:

- DoH, DoT, Private Relay или встроенный VPN на клиенте;
- IPv6 policy для управляемого source;
- порядок RouterOS mangle/raw/filter;
- DNS-кэш клиента после смены режима;
- совпадение source CIDR с карточкой устройства.

Тест только через системный `nslookup` не обнаруживает DoH приложения.
Сопоставьте внешний DNS-resolver с фактическим WAN/VLESS/Reverse/WireGuard
адресом. Проверьте, что WAN lane имеет `detour=direct-wan`, а VPN lane и tunnel
его DoH/DoT upstream используют тот же selector, что данные. Для remote user
проверьте отдельную auth/source lane: Reverse VLESS не должен получать прямой
DNS fallback.

## WireGuard-клиент показывает старый адрес или peer не найден

Карточка входящего WireGuard-клиента должна ссылаться на RouterOS peer `.id`.
Если public key или `allowed-address` изменены у того же peer, нажмите
«Обновить список»: прежний CIDR должен замениться текущими конкретными
IPv4-префиксами, а дубликат карточки появляться не должен.

Если peer удалили и создали заново, RouterOS выдаёт новый `.id`. Это не та же
identity, даже при совпадающем имени или адресе. Выберите новый peer в карточке
клиента и повторите Check. До этого Apply закономерно блокируется ошибкой
`wireguard_peer_missing`.

Для обычного клиента используется `/32`, для site-to-site peer допустима его
сеть. Default route `0.0.0.0/0` источником клиента не считается. Если старая
запись не содержит `source_peer_refs`, сохраните её после
однозначного выбора live peer; панель запишет стабильную ссылку.

## WireGuard-выход не показывается или не передаёт трафик

Если карточка сообщает, что live-инвентаризацию получить не удалось, нажмите
**Повторить** в самой карточке. Переход между разделами и F5 не должны менять
сохранённое положение переключателя: оно читается из черновика, а доступность
интерфейсов проверяется отдельным live-запросом. Сообщение о неполной
инвентаризации означает, что RouterOS REST не вернул хотя бы один из трёх
наборов: WireGuard interfaces, WireGuard peers или IPv4 routes.

Панель скрывает выключенные интерфейсы. У включённого интерфейса должен быть:

- хотя бы один включённый peer;
- один однозначный peer либо ровно один peer с `0.0.0.0/0`;
- актуальный handshake и рабочий endpoint;
- отсутствие пересечения локальных сетей с `198.18.0.0/15`.

Не добавляйте default route в `main`. После Check/Apply должны существовать
project-owned `sb-wg-*` table, source rule, return route и
`SB_WG_EGRESS_SOURCES`; трафик самого MikroTik при этом продолжает следовать
`main`. Если route card показывает недоступный технический узел, обновите live
inventory и убедитесь, что сохранённый interface существует с тем же именем.
При снятии выбора проверьте возврат исходного `allowed-address` peer.

## Подписка провайдера не обновляется

Откройте отчёт candidate: HTTP status, размер, timeout, формат и число
принятых узлов. Проверьте DNS, время, TLS-цепочку и наличие URL в SecretStore.
Пустой или повреждённый candidate не заменяет последнюю рабочую копию.

В форме редактирования сохранённый URL должен показываться полностью. Локальный
Xray-proxy проверяется с коротким тайм-аутом, после чего запрос продолжает
прямой WAN/VPN fallback; браузер ждёт итоговый ограниченный ответ control plane.
Если сервер отдаёт неподдерживаемую страницу из-за собственного определения
клиента, control plane автоматически повторяет получение в форматах v2rayNG и
Clash Meta; эта проверка выполняется только после ошибки разбора первого ответа.
Если первая попытка создания была отклонена валидатором, её URL удаляется
транзакционно, поэтому повторное сохранение не должно выдавать
`secret_not_provisioned`. При повторении ошибки проверьте права `0600` на файл
SecretStore и владельца каталога.

## Клиентская HTTPS-подписка не открывается

Проверьте выбранный режим публикации:

- **отдельный CDN-домен** требует публичный edge для ссылки и отдельное
  concrete DNS-имя origin, покрытое origin TLS-профилем. Origin здесь —
  SNI/Host CDN → шлюз, не обязательно отдельная DNS-запись, которую создаёт
  панель; edge не используется как неявный fallback;
- **использовать домен подключения** требует выбранного CDN-развёртывания;
- **прямая HTTPS-ссылка** требует свободную пару публичный IP:TCP-порт;
- **прямая + CDN** публикует оба адреса с одним непрозрачным сегментом.

У отдельного CDN сверяйте два независимых значения: публичный HTTPS-порт
должен быть открыт/поддержан на edge провайдера, а TCP-порт origin — совпадать
в настройках CDN, Nginx и RouterOS. Например, `443 → 18443` означает, что
клиент продолжает открывать обычный HTTPS/443, но CDN приходит на MikroTik/18443.

Приложению нужен полный URL из карточки клиента. Сегмент не содержит слов
`sub`, `subscription` или `links`. После ротации прежний URL сразу перестаёт
работать, поэтому клиенту нужно передать новую ссылку.

Прямая HTTPS-ссылка и VLESS REALITY не могут слушать один TCP-порт одного
публичного IP. CDN-подписка и несколько CDN-транспортов могут использовать
TCP/443 через разные SNI и пути. Hysteria 2 использует UDP и не конфликтует с
TCP/443.

Временного fallback для ссылки нет. Если публичный CDN/direct hostname не
настроен и не применён, панель должна вернуть ошибку конфигурации, а не выдать
адрес из окружения контейнера.

## Полный профиль импортирован, но карточка не маршрутизируется

Проверьте формат ответа по `X-SB-Profile-Format`. URI/base64 передаёт узлы без
индивидуальных правил. Для маршрутизации на устройстве нужен Xray JSON,
sing-box JSON или Mihomo YAML и включённая у пользователя **Индивидуальная маршрутизация**.

В Xray/sing-box/Mihomo-профиле найдите ожидаемые переносимые доменные правила.
Публичный клиентский профиль не должен содержать `geosite:*`/`GEOSITE`: мобильное
приложение может не иметь нужной секции локальной геобазы, и тогда ядро не
запустится. Домены всех выбранных карточек нормализуются и объединяются без
повторов. Полная таблица находится в
[CLIENTS.md](CLIENTS.md#как-карточки-попадают-в-клиентский-профиль).

**Индивидуальная маршрутизация** и дополняющие её **Точечные домены** включаются
только вручную: это сохраняет выбор, где делить трафик — на шлюзе или на клиенте.
Если новый профиль всё ещё сообщает об отсутствующем `geosite`, клиент использует
закешированную старую подписку:
обновите её, а при необходимости удалите только эту подписку и добавьте тот же
URL заново.

## Hiddify сообщает `SingboxParser Incorrect Json Format`

Проверьте `X-SB-Profile-Format`: Hiddify 4, Karing и sing-box должны получать
`singbox`, а не `mihomo`. Hiddify iOS 4.0.0 повреждает отступы удалённого Clash
YAML при загрузке, поэтому YAML нельзя использовать как автоматический формат
для Hiddify. Обновите подписку; если клиент сохранил старый документ, удалите
только профиль и добавьте тот же URL снова. Явная диагностика доступна через
`?format=singbox`.

## Hiddify сообщает `Connection refused` на `127.0.0.1:<случайный порт>`

Это loopback-порт Hiddify на самом устройстве, а не адрес SB Gateway и не
origin подписки. При удалённом импорте Hiddify сначала проверяет собственный
mixed-proxy, а если порт в этот момент открыт, выбирает
`PROXY localhost:<port>; DIRECT`; закрытие listener между проверкой и запросом
даёт `errno = 61` до чтения тела подписки
([HTTP-клиент Hiddify](https://github.com/hiddify/hiddify-app/blob/v4.0.4/lib/core/http_client/dio_http_client.dart#L80-L118)).
Однако импорт содержимого через буфер тоже не является полностью независимой
проверкой: Hiddify выбирает `addLocal`, записывает временный файл, а затем
передаёт его своему локальному core для разбора и валидации
([выбор local/remote](https://github.com/hiddify/hiddify-app/blob/v4.0.4/lib/features/profile/notifier/profile_notifier.dart#L63-L84),
[валидация local-профиля](https://github.com/hiddify/hiddify-app/blob/v4.0.4/lib/features/profile/data/profile_repository.dart#L179-L196)).

Сначала проверьте тот же URL с User-Agent Hiddify: ответ должен быть HTTP 200,
`Content-Type: application/json` и `X-SB-Profile-Format: singbox`. Если
серверный ответ корректен, отключите tunnel, дождитесь полной остановки core,
полностью закройте Hiddify и повторите после запуска. Если dev-сборка продолжает
попадать в гонку, перезагрузите устройство либо используйте актуальную
стабильную сборку.

Для диагностического импорта через буфер откройте именно `?format=singbox` и
убедитесь, что скопированное содержимое начинается с `{`, а не с URL или
base64-списка. Успешный импорт такого тела отделяет неисправность downloader.
Если то же тело снова даёт `errno = 61` на меняющемся localhost-порту, локальный
импорт не смог воспользоваться внутренним сервисом Hiddify; это не доказательство
ошибки JSON. В таком случае проверьте любую заведомо рабочую подписку в той же
сессии приложения, затем перезапустите или переустановите стабильную сборку,
предварительно сохранив нужные профили. Изменение DNS, транспортов или
маршрутных правил на сервере localhost-listener не исправляет. Такая же ошибка
импорта зарегистрирована upstream в
[Hiddify-Manager #5387](https://github.com/hiddify/Hiddify-Manager/issues/5387).

## CDN-транспорт не подключается

Проверьте четыре уровня:

1. Клиент использует домен раздачи и его SNI.
2. CDN передаёт запрос на правильный origin hostname и origin port.
3. TLS-профиль origin соответствует имени, которое CDN отправляет контейнеру.
4. RouterOS разрешает origin только официальным CIDR провайдера либо запросам с
   настроенным секретным заголовком.

Типовые причины:

- TLS 525/526: неверный SAN, цепочка, время или strict TLS;
- WebSocket 404: неверный Host или path;
- gRPC 502: отключён HTTP/2, неверный service name или h2c/TLS режим origin;
- HTTPUpgrade 403/404: WAF, transform или путь;
- XHTTP: режим, `extra`, путь и Host отличаются между клиентом и сервером.

Проверяйте edge через внешний интернет. Hairpin NAT может скрыть ошибку.

## Direct REALITY не подключается

Сверьте публичный TCP-порт, `serverName`, target, public key, Short ID и uTLS
fingerprint. Домен и target должны поддерживать правдоподобное TLS 1.3
рукопожатие. REALITY не использует CDN и обычный сертификат.

Проверьте конфликт публичного IP:TCP-порта с прямой HTTPS-подпиской или CDN
origin. Внутренние Xray-порты `11001`-`11004` к WAN не относятся.

### Проверка target показывает ошибку только для IPv6

Сравните результаты по каждому DNS-адресу. Успешный TLS 1.3 по IPv4 и
`tls_probe_handshake_failed` по AAAA означают, что контейнер не имеет
IPv6-маршрута к target. Панель показывает такой адрес предупреждением и
разрешает сохранить REALITY-транспорт.

Проверьте IPv6 route контейнера, если target должен работать по IPv6. Ошибки
сертификата, отказ target принять SNI и отсутствие ALPN `h2` для gRPC требуют
сменить SNI/target или исправить удалённый TLS. Панель продолжает блокировать
сохранение при этих результатах и при полном отсутствии успешных адресов.

## WAN-адрес MikroTik изменился

DHCP-клиент RouterOS обновляет аренду и default route. Контейнер сохраняет свой
veth-адрес, поэтому входящие listeners и исходящий трафик продолжают работать.

Поля **Hostname подключения** хранят внешний endpoint. Панель не заменяет их по
DHCP-аренде. Измените hostname включённых транспортов, выполните
Check/Plan/Apply, затем обновите подписки и статические Reverse VLESS-профили.
Закрепите адрес на upstream DHCP-сервере или используйте стабильное DNS-имя.

## Hysteria 2 не подключается

Проверьте UDP-порт, TLS SNI, сертификат, пароль и Salamander obfuscation.
RouterOS firewall должен разрешать UDP, а upstream не должен блокировать QUIC.
Параметры скорости показываются только на ядре, которое их применяет. Xray-core
не получает фиктивные лимиты sing-box.

При включённом UDP hopping проверьте весь опубликованный диапазон. Если Apply
сообщает пересечение с чужим dstnat или WireGuard, добавьте названный порт в
**Исключить занятые UDP-порты** либо выберите другой диапазон. Исключённый порт
не публикуется клиенту и не перехватывается управляемым NAT. После изменения
обновите подписку; старый профиль продолжит обращаться к прежнему списку портов.

## Reverse VLESS подключён, но трафика нет

Проверьте:

- reverse-клиент включён и доступен в маршрутных листах;
- выбраны только прямые REALITY-входы: Reality+Vision, gRPC+REALITY или
  XHTTP+REALITY; обычный WebSocket/CDN-вход использовать нельзя;
- удалённый Xray использует скачанную конфигурацию без ручной замены UUID;
- выбран хотя бы один серверный REALITY-вход;
- Raspberry Pi или другой reverse-host имеет рабочий интернет;
- сервер видит активную TCP-сессию, а не только сохранённую карточку.

Если узел `online`, но HTTPS заканчивается таймаутом, заново скачайте профиль в
панели, замените именно запущенный JSON на reverse-host и перезапустите каждый
экземпляр Xray. Актуальный экспорт содержит самодостаточные `finalRules` без
ссылки на `geoip.dat`: приватные/резервные назначения блокируются, публичные
разрешаются. Старый процесс может оставаться `online`, одновременно продолжая
отбрасывать весь пользовательский трафик.

Серверный контейнер должен показывать Xray-core 26.9.9, а удалённый reverse-host
— закреплённый 26.7.28 из header экспорта. Не считайте установленную TCP-сессию
достаточной проверкой: отдельно отправьте HTTPS через каждый Reverse transport.
Совместимость этой пары проверяется повторным end-to-end тестом.

Если внешний Xray показывает соединение XHTTP/gRPC, но карточка панели остаётся
`Недоступен`, проверьте запущенный JSON: у `streamSettings` должен быть
`network: "xhttp"` или `network: "grpc"`, а не только новое поле `method`.
Несовместимый клиент может установить внешний TCP/TLS-сеанс, но принять
неизвестный selector как TCP и не зарегистрировать ожидаемый reverse tag.
Повторно скачайте текущий экспорт и перезапустите reverse-клиент. Экспорт
использует стабильное поле `network`.

Для локального WireGuard-клиента сначала проверьте handshake, `rx` и `tx` его
peer. При `current-endpoint-port=0` и нулевых счётчиках пакет не дошёл до
MikroTik, поэтому одновременно не будут работать ни LAN, ни WAN-исключения, ни
основной маршрут панели. Это не неисправность Reverse VLESS.

Факт установления трёх TCP-сессий не доказывает передачу пользовательского
трафика. Сквозной и нагрузочный тест требует отдельного reverse-host.

## Клиент активен, но скорость равна нулю

Телеметрия по умолчанию обновляет моментальные значения каждые 15 секунд и
сохраняет накопленные счётчики раз в минуту. Проверьте Xray StatsService для
удалённого клиента и nft-таблицу `sb_gateway_client_telemetry` для локального.
Таблица считает трафик и не меняет маршрутизацию.

После перезапуска краткая задержка допустима. Постоянный ноль при реальном
трафике означает, что идентификатор клиента не связан со счётчиком либо
StatsService не включён в сгенерированной конфигурации.

## MTU и зависающие загрузки

Если небольшие страницы работают, а upload или gRPC зависают, выполните PMTU
test для каждого пути. Уменьшайте `tun_mtu` небольшими шагами. MSS clamp должен
действовать только на SB Gateway path. После изменения проверьте существующие
WireGuard, OpenVPN и другие VPN.

## IPv6 leak

При `block_managed` управляемый source не должен получать прямой публичный
IPv6. Неуправляемые устройства могут продолжать использовать IPv6. Проверьте
IPv6 address-list, filter и SLAAC privacy addresses.

Для remote VLESS режим `proxy_only` направляет IPv6 через назначенный selector.
При отсутствии здорового selector Xray отклоняет поток fail-closed.

## Обновление остановилось или оставило два контейнера

Во время probation два контейнера допустимы: новый работает, прежний остановлен
для отката. Успешное обновление требует 3 успешных health-проверки без
перезапуска; единичный timeout локального fetch не начинает всю проверку заново.
После подтверждения RouterOS должен оставить:

- один контейнер SB Gateway;
- один активный root-dir;
- без upload, hold-veth и rollback scheduler;
- без временных файлов SB Gateway в RouterOS Files.

При неуспехе worker запускает прежний контейнер и удаляет candidate. Не
удаляйте остановленный rollback-контейнер до завершения операции.

## Резервная копия не восстанавливается

Файл `.sbgw` зашифрован паролем панели, который действовал при его создании.
Введите этот пароль при восстановлении. Архив не содержит сам пароль панели и
активные сессии. Панель хранит до трёх последних архивов на SSD и дублирует их
в RouterOS Files.

При поломке SSD загрузите сохранённый `.sbgw` из браузера. Восстановление на
чистой установке проверяет формат, версию и целостность до замены данных.

## Полное удаление оставило объекты

После операции должны исчезнуть только объекты с точной меткой владельца
`SB-GATEWAY`, подтверждённый каталог проекта, управляемые backup и временные
файлы. Проверьте Container, Envs, Mounts, IP Firewall, Routes, Scheduler, Users
и Files. Чужие VPN, маршруты и файлы удалять нельзя.

Повторный запуск удаления должен быть идемпотентным. Если остался объект с
другим владельцем, сохраните его и исправьте ownership вместо ручного массового
удаления.

## Защищённый RouterOS Apply не запускается

1. Укажите реальный SSH-порт тестового RouterOS.
2. Разрешите REST-пользователю SSH только с IP контейнера.
3. Проверьте наличие SSH-клиента в образе.
4. При законной смене host key удалите сохранённый fingerprint из SecretStore и
   подтвердите новый.
5. Не отключайте Safe Mode или project-owned rollback scheduler вручную.

RouterOS откатывает незавершённую SSH-сессию. На RouterOS 7.24 панель намеренно
не открывает нестабильную SSH Safe Mode-консоль: локальный rollback scheduler
владеет транзакцией и запускает точный LKG при ошибке. На других версиях он
остаётся второй защитой и безопасным fallback при разрыве SSH. Candidate принимается
после трёх успешных health-проверок; лимит 12 последовательных промахов
применяется только к уже готовому live-процессу и не удлиняет первичное
переключение трафика.

## Ручной откат

Сначала используйте rollback в разделе **Эксплуатация**. При недоступной
панели запустите RouterOS recovery script из WebFig. Binary RouterOS backup
восстанавливает весь роутер и подходит только для аварии, которую нельзя
устранить экспортом SB Gateway или архивом `.sbgw`.
