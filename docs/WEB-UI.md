# Управление через Web UI

Документ соответствует SB Gateway 1.6.21 и серверному Xray-core 26.9.9.

## Доступ и сессия

Панель — основной интерфейс управления:

```text
https://<фактический-IP-контейнера>:9443
```

После создания пароля администратора ненастроенный шлюз показывает на экране
«Обзор» действие **Настроить шлюз**. Оно открывает мастер первого запуска;
закрытие мастера не применяет черновик, а действие остаётся доступным до первого
успешного Apply.

Новая установка начинает с клиентского режима: публикация HTTPS-подписки и все
серверные транспорты выключены. Домен и TLS-профиль требуются только после
явного включения соответствующей публикации или входа. Пустой список включённых
TLS-транспортов не блокирует Apply. Выключение CDN-транспорта также выключает его
развёртывания и снимает обязательность домена, origin и TLS-профиля. Пустая
стартовая TLS-заготовка не переносится в сохранённый черновик; профиль появляется
только после явной настройки серверной функции.

Локальный HTTPS панели при этом не зависит от публичного профиля: пока публичный
status-host не настроен, Nginx использует установочную пару
`/config/certs/bootstrap.pem` и `/config/certs/bootstrap.key` только для порта
управления. Сохранённая ссылка `ingress.tls_profile_id` на выключенный профиль не
создаёт публичный listener и не блокирует client-only Apply.

Пустые поля management CIDR и RouterOS ingress на экране настроек обозначаются
как заполняемые мастером и не имитируют сохранённые адреса. Пользовательский
порт панели по умолчанию — `17443`; RouterOS REST/www-ssl использует отдельный
высокий порт (`59443` в release bundle).

Доступ разрешён только при совпадении source CIDR и доверенного RouterOS
ingress-интерфейса. WAN-интерфейс запрещён валидатором. Для удалённого
администратора используйте точный адрес WireGuard/OpenVPN `/32`; панель через
WAN, CDN и VLESS ingress не публикуется. Nginx завершает management TLS, API
слушает `127.0.0.1:8080`.

Форма входа использует стандартные поля `username` и `current-password` и
отправляется обычным `POST` на тот же локальный origin. Галочка «Запомнить
данные» включена по умолчанию и разрешает браузеру использовать эти стандартные
autocomplete-подсказки; после её снятия форма отправляется с отключённым
autocomplete. Control plane проверяет
учётные данные, устанавливает `HttpOnly`/`SameSite=Strict` session cookie и
возвращает браузерный `303` в панель. Это позволяет встроенному менеджеру
паролей распознать успешный вход так же, как на локальных панелях роутеров: для
механизма не требуются публичный домен, ACME или Credential Management API.
Пароль не попадает в URL и не возвращается в HTML; при ошибке сервер передаёт
форме только безопасный код причины. Предложение сохранить пароль всё равно
остаётся решением браузера и не появится, если пользователь запретил сохранение
для адреса панели.

Management TLS остаётся локальным и не требует периодического выпуска
публичного сертификата. Доверие к локальному сертификату рекомендуется для
защиты от подмены внутри management LAN, но не является эксплуатационной
зависимостью входа или обновления панели.

При первом открытии в новом браузере панель предлагает выбрать русский или
английский язык и сохраняет выбор только в `localStorage` этого браузера.
Компактная кнопка `RU`/`EN` рядом с профилем администратора переключает язык
без Apply, перезапуска и изменения конфигурации MikroTik. Серверный HTML
остаётся русским безопасным fallback, поэтому вход и диагностика не зависят от
JavaScript-хранилища браузера.

Обе локали охватывают всю клиентскую оболочку и метаданные страницы: подписи, справочный текст,
валидацию форм, статусы, подтверждения, aria-метки и сообщения операций с
подставляемыми именами, портами и счётчиками. Даты, объёмы и скорости
форматируются в выбранной локали. Имена узлов и объектов, полученные из
пользовательских подписок или RouterOS, не переводятся и сохраняются дословно.
Полнота английского каталога и отсутствие русского fallback-текста в его
значениях проверяются отдельным Node-тестом.

Хешированные файлы `/_next/static/` получают долгий immutable-кеш. Их имена
меняются вместе с содержимым, поэтому старые CSS/JS не смешиваются с новой
версией, а перезапуск контейнера не оставляет панель в виде неоформленного HTML.
HTML, API и подписки по-прежнему отдаются с `Cache-Control: no-store`.

После входа администратор не вводит пароль повторно для обычного Apply,
обновления образа или полного удаления. Эти операции требуют preview и одной
явной галочки. Пароль спрашивается только там, где он технически нужен:
изменение пароля и расшифровка `.sbgw` при восстановлении.

## Черновик и применение

- Изменение формы сохраняется в Draft и не влияет на runtime само по себе.
- CRUD-запрос каждой сущности одним атомарным сохранением меняет данные и
  снимает `deployment_ready`; отдельного предварительного PUT из браузера нет.
  Ошибка проверки поэтому не оставляет частичное «лист не изменился, но
  готовность уже сброшена» и не создаёт лишнюю запись на SSD.
- Управляющий nginx принимает обычные JSON-формы до 2 МиБ. Первые 256 КиБ
  тела одного запроса остаются в ограниченном RAM-буфере, а редкое превышение
  уходит только в закрытый каталог `/run/sb-gateway/nginx-client-body`.
  Поэтому крупный маршрутный лист не зависит от прав системного temp-каталога
  и не пишет каждое сохранение на SSD.
- Верхний статус **Изменения · N** и кнопка **Применить (N)** появляются только
  при пользовательском отличии Draft от active generation.
- Число отражает логические пользовательские операции, а не количество
  изменённых JSON-полей. Внутренний сброс `deployment_ready`, сопровождающий
  реальное редактирование, отдельным изменением не считается. Наведение,
  клавиатурный фокус или нажатие на статус открывает компактный список того,
  что добавлено, изменено или удалено; значения секретов в него не попадают.
- **Сбросить** возвращает Draft к active generation.
- Check строит точный план, проверяет schema, секретные ссылки, Xray candidate,
  `nginx -t` и live RouterOS capabilities.
- Если точный Plan отклоняет черновик, окно Apply показывает каждую ошибку
  отдельно: пользовательское название параметра, причину и технический путь из
  ответа control plane. Поэтому обязательный домен, TLS-профиль или другое поле
  можно определить без DevTools; неизвестный текст backend сохраняется полностью.
- RouterOS topology/firewall change создаёт свежий backup и независимый
  rollback scheduler. На RouterOS 7.24 он сам владеет транзакцией; на версиях
  со стабильной консолью дополнительно включается SSH Safe Mode. Container-only
  change не запускает этот долгий путь.
- Если изменены только отображаемые названия и полный рендер доказал
  побайтовую неизменность runtime/RouterOS, план показывает **Только
  метаданные**. Apply не обращается к RouterOS, не создаёт backup, не
  перезапускает контейнер и обычно завершается на ARM64 CHR примерно за 2,5 с.
- Независимые таблицы live RouterOS preflight читаются ограниченно-параллельно.
  Один проверенный снимок переиспользуется в post-health, где заново читается
  только живое состояние контейнера; повторного полного inventory нет.
- Успешный Apply синхронно фиксирует active/LKG. Локальный зашифрованный `.sbgw`,
  RouterOS Files mirror и очистка старых управляемых backup выполняются
  persisted maintenance после ответа панели; несколько быстрых Apply
  объединяются в backup последней active generation.
- Проверенный candidate `xray.json` передаёт supervised restart одноразовый
  SHA-256 marker: повторный тест точного файла пропускается, но cold/manual
  restart и несовпадение hash сохраняют обязательный `xray -test`.
- Обновившийся renderer может один раз автоматически пересобрать только runtime
  после запуска новой версии. Пользовательские настройки при этом не меняются,
  а ложный pending Draft не создаётся. Версия структуры nginx-конфига
  проверяется до восстановления LKG: файл старой структуры не оживает после
  обновления образа, вместо него активная модель рендерится текущим шаблоном.

## Навигация

- Переход между разделами использует короткую View Transition без размонтирования
  общего shell. Если Chromium вытесняет ещё не завершённый переход новым,
  ожидаемые promise-rejection поглощаются, а выбранный раздел всё равно
  фиксируется; поэтому быстрые клики не вызывают ошибку страницы.
- Версия/канал RouterOS и container facts читаются общей live-инвентаризацией:
  один in-flight запрос разделяется между экранами, успешный результат
  кэшируется на 30 секунд, фоновое обновление выполняется раз в 5 минут и при
  возврате вкладки. Сохранённый импорт остаётся только резервным отображением,
  когда RouterOS REST временно недоступен.

### Обзор

Главная собрана как плотная операционная сводка. Верхняя пара карточек показывает
защиту локального интернета, реально включённые внешние входы с адресом и
портами, watchdog и суммарный трафик текущего UTC-месяца. Итог трафика имеет
компактный акцент и не конкурирует с состоянием защиты. Выключенные входы
свёрнуты в один счётчик и не занимают отдельные строки.

Строка **Количество перезапусков** берёт значение напрямую из RouterOS
`restart-count` и относится только к текущему запуску контейнера. Она
обновляется отдельным запросом статуса контейнера раз в 30 секунд; полный
RouterOS inventory для этого не запускается.
Состояние возврата VLESS показывается как **после восстановления**, без
смешения русского текста с внутренним термином `health`.

Таблица **Мониторинг сети** содержит одну компактную строку на каждого
локального или удалённого клиента и открывает его редактор напрямую:

- имя устройства/подключения и фактический адрес;
- тип **Локальный**/**Удалённый** и назначенный маршрутный лист;
- зелёную точку только при текущей активности;
- текущие uplink/downlink;
- суммарный трафик текущего UTC-месяца;
- действие **Настроить** без промежуточного поиска в разделе устройств.

Технические policy/transport IDs в строке не показываются. Remote users
учитываются Xray StatsService; local clients — отдельными counter-only
nftables rules. Пустой числовой замер (`null`, отсутствующее поле или пустая
строка) даёт компактную пару `↑ — бит/с · ↓ — бит/с`, а фактический ноль остаётся
`0 бит/с`. Маршрут всегда подписан пользовательским именем, а не внутренним ID.

Ниже показываются три последних реальных события с отдельным временем. При
отсутствии истории выводится честное пустое состояние; декоративных метрик и
дублирующей схемы маршрутизации на главной нет.

### Устройства

Здесь находятся локальные/VPN-клиенты и удалённые VLESS-пользователи.

Для локального клиента задаются имя, source CIDR либо общий охват всех устройств
LAN/Wi-Fi, маршрутный лист, режим публичного трафика и поведение при отказе
контейнера. Общий режим показывает найденные IPv4-подсети интерфейсов списка
RouterOS `LAN`; динамические DHCP-клиенты внутри них не требуют отдельных
карточек. Точечная карточка всегда имеет приоритет над общей независимо от
порядка создания. Проверка доступности точечного `/32` не блокирует сохранение
общего режима: в нём кнопка **Добавить** проверяет LAN-подсети, а не строки
статических DHCP-аренд. В карточке удалённого
пользователя поле **Подписка** показывает только число включённых узлов,
например `4 узла`; полный состав доступен в title/настройках и не раздувает
строку.

При выборе источника **WireGuard** список строится по peers, а не по
интерфейсам: одна компактная строка соответствует одному peer и переключает все
его точные IPv4 `/32`. Имя peer, адреса и справочное имя интерфейса показаны в
одной строке. LAN и PPP используют ту же компактную раскладку: comment/имя,
адрес и дополнительные факты не образуют второй ряд. Поэтому несколько клиентов
общего интерфейса назначаются разным маршрутным листам независимо. Сохранённая
стабильная ссылка на peer позволяет форме автоматически заменить старый CIDR после изменения
`allowed-address`, не создавая дубликат клиента. Check, Plan и Apply повторяют
это сопоставление по live-инвентарю; если peer удалён и создан заново с другим
RouterOS ID, применение блокируется до явного повторного выбора.

В редакторе удалённого пользователя:

- поле **Имя подключения** расположено в верхней строке формы;
- выбираются доступ к LAN, маршрутный лист и client TUN CIDR;
- рядом с форматом подписки выбирается общий для узлов пользователя **uTLS
  fingerprint**; значение по умолчанию — **Chrome**;
- транспорт показывается пользовательским названием и адресом, без
  технического ID вроде `direct-reality`;
- снятая галочка транспорта исключает его из подписки, но не удаляет серверный
  профиль;
- новый включённый транспорт добавляется существующим пользователям
  автоматически, если режим подписки пользователя — автоматический;
- переключатель пользователя расположен после списка транспортов, перед
  действиями формы. Повторяющиеся справочные карточки про UUID, fallback и
  отдельное сохранение не показываются: UUID по-прежнему создаётся автоматически,
  а применение Draft выполняется общей кнопкой панели.

Секция **Полный профиль · Xray / Sing-box / Mihomo** намеренно находится в серверной
панели: SB Gateway формирует клиентскую конфигурацию. Индивидуальная
маршрутизация, автоматический резерв и блокировка рекламы передаются только в
полном профиле, не в URI/base64 и не в Reverse-мосте. LAN-доступ дополнительно
ограничивается на сервере. Xray-only параметры не выдаются за настройки
серверного входа.

Поле **Стек TUN** по умолчанию использует режим **Автоматически**. В sing-box
поле `stack` при этом не фиксируется, чтобы поддерживаемый стек выбрало само
ядро; Mihomo получает `mixed`. Ручные `system`, `mixed` и `gvisor` переносятся
только в полный sing-box/Mihomo-профиль. Xray JSON, Happ URI и Streisand эти
чужие поля не получают. VLESS-прокси Mihomo получают `packet-encoding: xudp`.

Общий режим **Все устройства LAN / Wi-Fi** использует только действительные
IPv4-подсети интерфейсов RouterOS из списка `LAN`. Адреса `/32`, выключенные и
`invalid` адреса, а также интерфейсы, одновременно относящиеся к `WAN` или
WireGuard, исключаются. Поэтому ошибочное включение WAN/VPN-интерфейса в список
`LAN` не расширяет общий клиентский маршрут.

Новый DHCP-клиент внутри уже сохранённой LAN-подсети автоматически попадает под
общую политику. Если для его точного `/32` включить отдельную карточку, её
маршрутизация и DNS срабатывают раньше общей подсети; остальные адреса продолжают
использовать общий маршрут.

Кнопка выдачи подписки возвращает полный HTTPS URL только явным действием.
Сохранённый секретный path в обычной форме назад не раскрывается.

### Маршрутизация

Пользователь задаёт только **Название маршрута**. Технический ID
создаётся автоматически из этого имени, проверяется на уникальность и после
создания остаётся стабильным для внутренних ссылок. В карточках, списках и
выборах показывается название, а не ID. В таблице устройств ячейка под уже
подписанным столбцом **Маршрутный лист** содержит только это название без
повторного префикса.

Маршрутный лист имеет два базовых режима:

- **VLESS + WAN** — остальной публичный трафик идёт через выбранную
  VPN-политику; сервисные исключения идут через WAN;
- **WAN + VLESS** — остальной публичный трафик идёт через WAN;
  те же сервисные исключения идут через выбранную VPN-политику.

В режиме приоритета число слева от узла открывает его список разрешённых
сервисов. Отмеченные сервисы сразу видны в строке после подписи узла как
`Доступ: …`, ещё до сохранения формы. После Apply сайт, приложение, API, DNS и
WebSocket совпавшей карточки используют отдельный fail-closed selector: он
направляется в текущий активный узел только при установленной для этого узла
галочке; без неё сервис блокируется, а не утекает через основной или WAN-маршрут.

Если ни одного исключения не выбрано, действует только первый выход режима.
Новые исключения добавляются карточками и поиском **Добавить сервис вручную из
доверенного каталога**. Один и тот же механизм работает в обоих режимах:
выбранный сервис всегда идёт по противоположному основному маршруту. Каталог
принимает имя сервиса, домен или URL, но сохраняет только проверенный полный
service pack из `v2fly/domain-list-community`; recursive includes собирают
сайт, API, WebSocket/CDN и другие зависимости. Произвольный непроверенный домен
молча не добавляется, а ошибка обновления не заменяет последнюю рабочую копию.
Известная внешняя runtime-зависимость может быть добавлена узким reviewed
fallback поставляемой карточки. Штатная карточка `binance` включает сайт,
официальные API-домены и AWS WAF token host на том же выходе, но не превращает
весь общий WAF/CDN в исключение. Карточка российских операторов связи закрепляет
`sibset.ru`, `sibseti.ru`, `lk.sibseti.ru` и `211.ru` в релизе независимо от
доступности ежедневного каталога.
Перед Apply Xray-кандидат дополнительно отклоняет пустую карточку или карточку
без поддерживаемых условий. Поэтому ручная карточка из каталога получает тот
же recursive dependency graph и fail-closed проверку, что встроенная; ввод
одиночного произвольного домена не выдаётся за полный пакет сайта.

Совместимый внутренний ключ `direct_domains` не очищается при переключении
режима или редактировании старого листа, но сырой textarea для него в обычном
Web UI не показывается. DNS управляемого клиента перехватывается по TCP/UDP 53.
В блоке **DNS по маршруту** WAN и VPN получают независимые resolver:
WAN использует RouterOS/provider DNS или выбранный прямой resolver, VPN —
отдельный DoH/DoT. Соединение к VPN DNS upstream идёт через тот же selector,
что и данные, включая Reverse VLESS и WireGuard; проверка обязана исключать
утечку через другой resolver.

Все пользовательские сервисные карточки следуют противоположному основному
маршруту: WAN в режиме `VLESS + WAN`, выбранная VPN-политика в режиме
`WAN + VLESS`. Отдельным всегда-прямым правилом остаётся только включённый
BitTorrent.

Узлы выбираются в режиме **Лучший доступный** или **Приоритет**. В общей
таблице за 24 часа/7/30 дней видны доступность, потери, медиана и p95 полного
HTTPS-запроса (DNS + соединение + TLS + HTTP), скорость, число замеров и разница
с активным узлом. Таблица использует отдельные колонки для ранга, узла,
доступности/потерь, медианы, скорости, p95, разницы с активным и числа замеров.
Пока замеров нет, карточка показывает один статус вместо набора прочерков.
Переключение требует hysteresis и cooldown; существующие соединения по
умолчанию не разрываются.

Экран маршрутизации следует единому вертикальному сценарию: раскрываемые
маршрутные листы с очередью резервирования, общая таблица качества, полноширинные
Reverse VLESS и WireGuard, затем равная пара IPv6/совместимости и DNS по
маршруту. Между самостоятельными карточками используется шаг 16 px. На узком
экране карточки выстраиваются в одну колонку без горизонтальной прокрутки.
Общая кнопка **Сохранить** записывает все поля этого экрана одним Draft и после
его повторной загрузки сохраняет видимое подтверждение **Маршрутизация
сохранена. Примените изменения.**; успешная запись не выглядит как бездействие.
При входе в раздел все маршрутные листы свёрнуты. Раскрытый лист остаётся
раскрытым после обновления страницы в той же вкладке, но переход в другой пункт
меню сбрасывает это временное состояние.
В таблице качества узел показывается вместе с маршрутным листом в скобках, а
доступность — вместе с процентом потерь; обе пары занимают по одной строке.
Точки состояния и маркер `A` используют одну колонку и не сдвигают подписи строк.

Форма **Настроить маршрутный лист** повторяет компактный рабочий макет: её шапка
и нижние действия остаются на месте, а прокручивается только содержимое. Сначала
выбираются серверы в дереве групп/стран/городов, после него настраивается очередь
приоритетов выбранного набора. Дублирующий блок текущего состояния в форме не
показывается — фактическая телеметрия остаётся в таблице качества. Само дерево и сетка
сервисных карточек прокручиваются независимо при переполнении; карточки не
увеличивают высоту формы. Мета-строка показывает категорию и только особый тип
правила; обычное ежедневное расписание в каждой карточке не повторяется. Поле
ручного поиска в доверенном каталоге находится
сразу под карточками и перед переключателями Torrent/стратегии домена/точечных
доменов и содержит только краткое описание поиска. Поля дополнительных порогов
держат общую линию ввода, а включение листа оформлено компактным переключателем.
Переключатели включения маршрутного листа, устройства, удалённого пользователя,
подписки, транспорта и TLS-профиля используют одну полноширинную строку: текст
слева, switch справа. Включённая сущность получает зелёную подложку, выключенная
остаётся нейтральной; предупреждающие и опасные варианты сохраняют собственные
цвета. В нижней панели редактора удаление находится рядом с **Отмена** и
**Сохранить изменения**.
Подложка редактора не использует дорогой blur; невидимые карточки отрисовываются
отложенно внутри изолированной области прокрутки. На мобильном экране поля
переходят в одну колонку без горизонтального scroll.

При начальной загрузке подробный Xray status запрашивается одновременно с
компактным bootstrap-снимком, а после Apply/Reset оба снимка обновляются вместе.
Минутное обновление краткого runtime status сливается с последним подробным
selector history. Поэтому блок **Качество узлов** не исчезает между двумя
запросами: обновляются только фактические значения строк. Если подробный запрос
ещё не завершился, карточка пишет **Сверяю с ядром…** и не выдаёт Draft за факт.
Версия контейнера в системном блоке также появляется только из фактического
overview-снимка; до его получения показывается нейтральный прочерк, а не
историческое значение релиза.

Все разделы используют одинаковую 56‑px верхнюю панель и компактную типографику
заголовков по образцу маршрутизации. Документ постоянно резервирует место под
вертикальную полосу прокрутки: короткие и длинные разделы имеют одинаковую
рабочую ширину, поэтому статус и кнопки панели не сдвигаются при навигации.
Переключение через боковое меню плавно заменяет только рабочую область; для
системной настройки уменьшенного движения переход выполняется без
пространственной анимации.

Reverse VLESS показан компактными строками: состояние, имя, копируемый короткий
ID, серверные входы и действия помещаются в одну линию на desktop. Кнопка
**Конфиг** остаётся действием конкретного клиента. В переключателе входов
показываются полные профили входа — **Reality + Vision**, **gRPC + Reality** и
**XHTTP + Reality**; внутреннее значение `reality` не подменяется общим для них
названием протокола VLESS.

Готовые сервисные карточки можно скрыть из текущего маршрутного листа кнопкой
`×` в углу и затем вернуть одной командой. Пользовательская карточка той же
кнопкой удаляется из конфигурации и очищается из всех ссылок. Отдельная карточка
Ozon не показывается: она входит в **Маркетплейсы, объявления, доставка и
ритейл РФ**. Следом за транспортом идут операторы связи, российские медиа и
образовательные/рабочие/ИТ-сервисы, затем широкая карточка всей зоны RU/РФ.

Reverse VLESS-клиент выбирает один или несколько включённых direct server
inbounds (REALITY, gRPC+REALITY, XHTTP+REALITY), использует один UUID как пул
соединений и предоставляет скачиваемую Xray-конфигурацию. Реальный egress и
нагрузка проверяются после подключения Raspberry Pi/VPS.
Обычные WebSocket, gRPC+TLS, HTTPUpgrade и XHTTP+TLS в этом списке не
показываются и отклоняются сервером: они относятся к клиентским/CDN-входам, а
не к прямому reverse bridge.

TCP-параметры direct REALITY находятся в дополнительных настройках. Без
ручной настройки серверный inbound и Xray JSON, включая Reverse VLESS,
получают Keep-Alive `30` секунд простоя / `10` секунд интервала и
`tcpUserTimeout=60000` мс. Это стартовый профиль, не гарантия времени failover.
Существующие пользовательские значения сохраняются; сброс рекомендаций
восстанавливает этот набор. Выключатель отключает только Keep-Alive, в том
числе встроенный outbound-default Xray. Независимый `tcpUserTimeout=0`
отключает принудительный таймаут; положительное значение действует в Linux.
После изменения Reverse VLESS JSON нужно скачать и установить заново.

Для `gRPC + TLS` тот же блок `30 / 10 / 60000` настраивает только исходящий
TCP-сокет Xray-клиента до выбранного CDN. Значения попадают в обычный Xray JSON
каждого включённого CDN-развёртывания. Соединения CDN → origin и локальный
Nginx → Xray имеют собственный жизненный цикл и этим блоком не управляются.
Reverse VLESS использует прямые серверные входы, поэтому этот CDN-блок в него
не переносится.

TCP-параметры не передаются через VLESS URI/base64 и Mihomo YAML: в этих
форматах ими управляет клиентское приложение. Формат подписки автоматически
не меняется на JSON. В стандартном Xray 26.9.9 `tcpUserTimeout` не реализован
для Darwin/iOS; его действие на iPhone/Happ не обещается даже при импорте JSON.
Keep-Alive не проверяет работоспособность origin за отвечающим CDN.

Reverse VLESS, WireGuard, IPv6/совместимость и оба DNS-профиля сохраняются одной
кнопкой после последней карточки. Рядом расположена кнопка локального сброса
несохранённых полей к загруженному черновику. У Reverse VLESS нет отдельной
кнопки сохранения. Добавление, удаление и скачивание конфигурации остаются
действиями конкретной строки.

В полноширинной карточке **WireGuard-выходы** панель показывает WireGuard как
выход в интернет.
Имя выхода и его готовность располагаются в одной строке; статус не создаёт
отдельный второй ряд и не увеличивает высоту карточки.
Раздел монтирует форму только после загрузки черновика, поэтому переход из
другого раздела и полная перезагрузка показывают одинаковое сохранённое
состояние переключателя. При открытии раздела панель отдельно запрашивает
актуальные интерфейсы, peers и IPv4-маршруты через RouterOS REST. Пока запрос
идёт, карточка показывает загрузку; при ошибке сохранённый выбор не
подменяется, а внутри карточки доступна повторная попытка.
Панель показывает только включённые интерфейсы RouterOS и только имя/статус в
компактной строке `WG · <интерфейс>`. Выключенные и неоднозначные interfaces не
предлагаются. Пользователь не вводит страну, город, `allowed-address` или route:
после Apply full-tunnel peer и отдельная `sb-wg-*` table подготавливаются
автоматически только для source-трафика SB Gateway. `main` route MikroTik не
меняется, а исходный peer восстанавливается при снятии выбора.

Список WireGuard ограничен по максимальной высоте и получает вертикальный scroll
только при переполнении, поэтому большое число выходов не раздувает страницу.
Выбранные выходы сортируются первыми; остальные сохраняют порядок
live-инвентаризации RouterOS.

Reverse VLESS использует тот же принцип: список клиентов прокручивается только
при переполнении, а включённые клиенты поднимаются вверх сразу после
переключения. Карточки Reverse VLESS и WireGuard идут отдельными полноширинными
секциями, как в основном рабочем потоке экрана.

Факты IPv6 считаются доступными при `live_available=true`, включая ответ
`summary_source=live-cache`. Такой ответ содержит последнюю полученную через
RouterOS REST инвентаризацию и не показывается как отсутствие данных. Статус
**Обновляется** используется только до первой live-инвентаризации.

Внизу раздела находится один общий блок **Мониторинг маршрутов**. Он задаёт
интервалы для всех листов и не дублируется в каждой карточке. Значения по
умолчанию: доступность активного узла — 3 с, повтор после
ошибки — 2 с, поиск выхода из блокировки — 15 с, оценка качества активного узла
— 60 с, резервов — 300 с, полный обход — 1800 с. Размер порции **Авто** означает
до двух проверок за цикл для URLTest и до трёх для приоритетного режима.
Карточка не имеет отдельной кнопки сохранения: её значения входят в общую
кнопку **Сохранить** внизу раздела маршрутизации.

Редактор отдельного листа отвечает только за правила выбора: размер рабочего
пула URLTest, окно и пороги качества, число подтверждений отказа и
восстановления, а также защиту от обратного переключения. Эти поля не
перезаписывают общие интервалы мониторинга.

История **Качество узлов** обновляется раз в минуту без перезагрузки страницы.
Таблица показывает максимум 10 строк выбранного листа после сортировки: сначала
активный узел и текущие рабочие резервы, затем доступные фоновые кандидаты и
остальные пригодные узлы по сочетанию текущей скорости и задержки. Накопленная
доступность и потери разрешают равенство и сортируют кандидатов без полного
текущего измерения, но не вытесняют более быстрый и достаточно стабильный узел.
Кнопки листов нумеруются сверху вниз; выбор хранится по ID и сохраняется при
переименовании и перестановке листов. После удаления выбранного листа берётся
первый оставшийся. Нормализация выбора выполняется до commit дочернего дерева,
без дополнительного обновления всей таблицы из React effect.
При усечении виден счётчик «Показано 10 из N»; сбор статистики не ограничивается.
Раскрытый лист показывает **Узлы маршрута**, а не обещанную очередь резервов:
состав берётся из применённого runtime, включая Reverse/WireGuard, без усечения
лимитом активного пула. До первого применения используется инвентаризация.
Свежие ID подписки не смешиваются со старым применённым набором. Порядок:
активный, доступные резервы в порядке shortlist, доступные фоновые, непроверенные,
недоступные. Одинаковые названия не склеиваются. При полном совпадении исходных
названий среди всех узлов маршрута протокол добавляется после названия независимо
от подписки: `(WS)`, `(R)`, `(gRPC)`, `(XHTTP)`, `(HU)`, `(H2)`, `(WG)`, `(REV)`;
Reality поверх другого транспорта — например `(gRPC+R)`. Если совпадают и имя,
и протокол, интерфейс добавляет публичное название подписки; только для полностью
неразличимых дублей одного источника используется стабильный номер `#N`.
Метаданные берутся из той же применённой генерации, что и ID; до её обновления
возможен fallback к инвентаризации подписки только по точному ID. Никаких догадок
по названию сервера и зависимости от формата конкретного провайдера нет. Разные
исходные названия не получают лишних суффиксов.
При наведении на название узла отображаются полное название и имя подписки —
в активном маршруте, раскрытом списке и таблице качества. Видимых кодов провайдера
(`П1`, `П2`) нет; принадлежность определяется по `subscription_id`, не по имени узла.
Они идут компактной адаптивной сеткой, на узком экране — одной колонкой.
Весь выбранный набор входит в runtime и проверяется малыми партиями в фоне.
Рабочий пул (`shortlist`) формируется по результатам проверок: активный путь
сохраняется, остальные места занимают подтверждённые доступные резервы.
Они подписаны **Рабочий резерв**; доступные за пределами пула —
**Доступен · фоновая проверка**. Непроверенный узел серый, недоступный красный.
Счётчик резервов учитывает только доступные неактивные узлы рабочего пула.
`max_active_candidates` ограничивает размер этого пула, не набор проверяемых
серверов и не таблицу. Недоступный резерв не удерживает место при наличии замены.
Поле **Узлов в активном пуле** показывается только в URLTest: редактор листа →
**Дополнительные параметры переключения**, диапазон 1–10. Сохранённое значение показано явно;
изменение сохраняет `max_active_candidates` и соответствующий размер shortlist
`max_probe_candidates`, вступает в runtime после Apply. Число активных мест в
редакторе учитывает этот предел только в URLTest. В приоритетном режиме поле
скрыто, число мест определяется полным набором выбранных серверов, а список
перестановки направлений не усекается. Сохранённый лимит URLTest не ограничивает
приоритетную очередь и остаётся доступным при возврате к URLTest.
В URLTest доступность и quality сначала допускают резерв к выбору. Среди
допущенных узлов порядок задаёт сочетание скорости и текущей HTTPS-задержки;
суточные потери служат только последним разрешением равенства. Медленный
высокодоступный узел остаётся аварийным запасом на случай отказа быстрых. Режим
приоритета сохраняет пользовательский порядок. Значения таблицы за 24 часа —
исторический агрегат, а не буквальный снимок короткого окна последнего решения.
Замена резерва не означает немедленного переключения исправного активного сервера.
Удаление именно активного узла — отдельный штатный случай: после Apply уже
проверенный рабочий резерв выбирается сразу, получает cooldown от повторного
планового переключения и отображается после подтверждения Xray. Такое изменение
обновляет health contract горячо, не перезапускает Xray, monitor или watchdog и
не обрывает существующие соединения; новые соединения идут через резерв. Если
проверенного резерва нет, лист временно закрывается до первой успешной аварийной
проверки, а не выбирает непроверенный сервер вслепую. При неизбежном перезапуске
ядра (обновление версии или другого Xray-параметра) тот же выбор выполняется
startup-helper до допуска transparent routing; холодный `block` без истории
заменяется первым кандидатом текущего листа.
Подтверждённый выбор и состав узлов опрашиваются отдельно каждые 5 секунд только
на видимом экране **Маршрутизация**, а также после Apply, включая `shortlist`. Короткий запрос не
передаёт историю и не запускает probes. Новый активный узел показывается до
первого замера; пока статистики нет, значения остаются пустыми, а не нулевыми.
Поздний ответ с историей не перезаписывает более свежий `runtime_observed_at`.
После смены применённой ревизии перечитывается и инвентаризация подписок.
Переключатели 24 часа / 7 дней / 30 дней меняют агрегат
сразу. Проценты рассчитываются только по выполненным пробам: простой самого
RouterOS или контейнера не считается потерей, а календарные окна 7/30 дней не
подтягивают замеры старше выбранного периода. Если активно несколько маршрутных листов, все их активные узлы с
маркером `A` располагаются первыми и сортируются между собой по качеству.
Маркер и подпись активного выхода берутся только из `runtime_selected` при
`runtime_confirmed=true`, то есть после обратного чтения Xray selector. Пока
ядро не подтвердило выбор или вернуло другой member, панель показывает
**Не подтверждено ядром** / **Переключение не применено** и не подменяет факт
сохранённым значением формы.

В шапке маршрутного листа, очереди и таблице качества флаг из имени узла
заменяется локальным SVG; при наличии country metadata она используется как
резерв. Название провайдера и остальные символы сохраняются, флаг не дублируется.
В выпадающем списке приоритетов страна, город и провайдер не дописываются
повторно, если они уже присутствуют в полном имени узла; краткая строка под
полем и суффикс option содержат только новые сведения, например транспорт.
Размер флага фиксирован: 16×12 px; он выровнен по центру и не увеличивает строку.
Если страна неизвестна, она не угадывается. Это устраняет буквенные `CA`/`DE`
вместо emoji-флагов на Windows. Локальные ассеты flag-icons 7.3.2 (MIT) лежат
в `public/flags`, без runtime-зависимости или обращения к внешнему CDN.
Затем по тем же критериям показываются резервные узлы; нумерация соответствует
этому видимому порядку.

### Подключения

Карточки разделены на:

- **Через CDN + TLS**: WebSocket, gRPC, HTTPUpgrade, XHTTP;
- **Прямые + REALITY**: Vision, gRPC+REALITY, XHTTP+REALITY;
- **Прямые TLS / QUIC**: gRPC+TLS Pin, Hysteria 2;
- TLS-профили, независимые резервные VLESS и HTTPS-ссылка подписки.

Краткая строка показывает имя, адрес/режим, состояние и кнопку
**Настроить**. TLS-профиль и независимый VLESS не разворачивают вторую карточку
под строкой: полная форма открывается во всплывающем окне. Это же правило
используется для транспортов и lifecycle-операций.
Заголовок и доступные поля редактора берутся из сохранённого типа транспорта,
а не из его технического ID. Поэтому импортированная или созданная через API
запись с произвольным ID показывает то же полное редактирование, что и штатный
транспорт соответствующего типа.
Для прямого XHTTP+REALITY рекомендуемый режим — `auto`: Xray выбирает
`stream-one` на REALITY-клиенте, а сервер принимает все XHTTP-режимы. После
смены режима экспортированный Reverse VLESS JSON нужно заменить на удалённом
bridge-клиенте; транспорт при этом остаётся XHTTP+REALITY.
Рекомендуемый XMUX-профиль для клиентского экспорта задаёт
`maxConnections=3` и `maxConcurrency=0`. Он ограничивает число одновременно
открытых Reality/TLS-соединений и тем самым не превращает параллельные потоки
мобильного клиента в неконтролируемый рост соединений. Патч XTLS отдельно
защищает контейнер от аварии при крупной записи, поэтому стабильность клиента
не должна достигаться ценой агрессивного `maxConcurrency=1`. Пользователь может
изменить оба поля, но одновременно
положительным остаётся только одно.
При уходе с `packet-up` панель автоматически заменяет допустимые только там
`uplinkDataPlacement=header|cookie` и `uplinkHTTPMethod=GET` на совместимые
`auto` и `POST`; сохранённые поля поэтому совпадают с реально запущенным Xray.
Статические подсказки под заголовками групп не выводятся. Срок сертификата
показывается в TLS-профиле один раз, а его применения — компактным количеством;
соседние секции разделены единым вертикальным интервалом.

В форме прямого TLS/QUIC транспорт только выбирает существующий TLS-профиль:
создание, загрузка PEM, выпуск и замена сертификата доступны исключительно в
редакторе **TLS-профили**. Профиль без полной пары показывает короткое указание
на этот редактор; форма транспорта не создаёт секреты и не изменяет сертификат.
Редактор TLS-профиля предлагает три источника: загрузка PEM, автоматический ACME
и **Локальный CA · TLS Pin**. В локальном режиме достаточно указать конкретный
DNS SNI: при первом сохранении control plane создаёт `MyRootCA` и leaf на 10 лет.
Обычное сохранение профиль не ротирует; для замены пары есть отдельное действие
**Пересоздать сертификат**. После пересоздания клиент должен обновить подписку.
У Hysteria 2 и gRPC+TLS Pin выбор профиля с одним конкретным DNS SAN сразу подставляет это имя
в существующее поле **TLS SNI**. Если конкретных SAN несколько, они доступны в
том же поле как варианты; ручной ввод сохраняется только когда выбранный
сертификат покрывает это имя.
Для gRPC+TLS Pin pin текущего leaf-сертификата обязателен и не настраивается
отдельной галочкой. При замене сертификата подписку клиента нужно обновить.
Локальная регрессия этой границы проверяет синтетическую DOM-разметку; browser
capture и проверка на развёрнутом роутере остаются отдельными приёмочными
шагами.

Провайдерские подписки показаны компактными строками. В строке нет служебного
ID и надписи `URL скрыт`; одно меню **Действия** содержит проверку, список узлов
и настройку. В форме настройки URL отображается полностью как обычное
редактируемое однострочное поле с горизонтальной прокруткой. Значение читается из SecretStore только после проверки
сессии администратора и не попадает в audit log. Дополнительные пути обновления
показаны в блоке **Пути обновления**. Поле названия подписано **Имя подписки**.
В редакторе нет вводного текста о хранении URL и повторяющих поля пояснений:
остаются названия настроек, краткий выбранный путь, реальные статусы загрузки,
ошибки и данные провайдера. Удаление пояснений не меняет параметры обновления.
Имя и интервал стоят в первой строке, URL занимает всю ширину следующей.
**Пути обновления** — три взаимоисключающих режима: **WAN** (direct=true,
vpn=false), **WAN → VPN** (оба true), **VPN** (direct=false, vpn=true).
Они меняют прежние параметры `refresh_via_direct` / `refresh_via_vpn`, а не
вводят новый серверный режим. При включённом VPN ниже видны переключатели
**Рабочие каналы** и **Резервные VLESS**. Переход на WAN скрывает их, сохраняя
выбор для возврата; проверки наличия пригодного пути перед сохранением остаются.
У radio-группы работает клавиатурный выбор и видимый focus; на узком экране
поля и VPN-переключатели идут одной колонкой. **Подписка включена** находится
в конце формы, после данных провайдера.

Срок и расход трафика берутся из `Subscription-Userinfo` последнего успешного
обновления. Страница подключений получает их одним компактным запросом
`GET /api/v1/status?view=subscriptions`, без списков узлов и без запроса к
провайдеру. Запрос повторяется каждые 30 секунд только при видимой странице;
одновременные запросы не накапливаются. При переходе между разделами и временной
ошибке сохраняется последний полученный снимок метаданных в памяти браузера.
Поздний ответ не откатывает более свежий `refreshed_at`. До первого ответа
показана загрузка, а отсутствие срока у провайдера не смешивается с ошибкой
загрузки. Успешное новое обновление без срока может убрать прежнюю дату —
панель не выдаёт старые сведения за новый ответ провайдера.

#### ACME-DNS для других DNS-провайдеров

В режиме сертификата **Автоматически · ACME** список DNS-провайдеров содержит
**ACME-DNS · другой провайдер**. Только этот вариант показывает HTTPS-адрес
сервиса, импорт JSON регистраций и пары полей CNAME. Готовые DNS-адаптеры
сохраняют прежние поля. **Проверить CNAME** не выпускает сертификат и не проверяет
API-ключ; загрузка JSON и смена адреса не сохраняются до явного сохранения/выпуска.
После смены URL ключи загружаются заново, поздние ответы прежней проверки не
подменяют результат новых настроек. Для сохранённого профиля видны CNAME,
но не учётные данные. Колонки CNAME складываются на узком экране.
Настройка сервиса, формат нескольких доменов, доверие и границы проверки:
[ACME-DNS](acme-certificates.md#acme-dns-для-неподдерживаемого-dns-api).

#### Перенос TLS-профиля

В окне настройки TLS-профиля кнопка **Экспорт** находится между удалением и
отменой, доступна при наличии сохранённой TLS-пары;
**Импорт** находится рядом с заголовком **TLS-профили**, в том числе при пустом
списке. Экспорт показывает имя профиля и просит задать и повторить пароль
архива (от 12 символов, до 256 байт). **Скачать архив** передаёт браузеру файл `.sbtls`;
сообщение подтверждает подготовку скачивания, а не сохранение файла на диск.
Архив содержит приватный ключ, для ACME — доступ к DNS API, а для локального CA —
его сертификат и приватный ключ. Пароль следует хранить отдельно. Состав и
ограничения описаны в [ACME и сертификаты](acme-certificates.md).

Импорт принимает файл `.sbtls` и пароль архива. **Импортировать** создаёт новый
выключенный профиль без изменения существующих подключений. После успеха
нужно проверить настройки, включить профиль и автопродление, назначить его
подключениям и выполнить Apply. Если профиль создан, но список не обновился,
окно предлагает обновить страницу и не повторять импорт.

Оба окна сохраняют белую поверхность и зелёное основное действие панели;
каждое решает одну задачу. Модальный диалог удерживает клавиатурный фокус,
блокирует фон и возвращает фокус к вызвавшей кнопке после закрытия. Escape
закрывает окно только вне выполнения запроса; во время запроса поля, повторная
отправка и отмена недоступны. Ошибки объявляются внутри окна, успешный результат
показывается отдельно. При потерянном ответе импорта повторная отправка
блокируется: сначала нужно закрыть окно и обновить список TLS-профилей.

Проверка этих диалогов ограничена синтетическим UI на ширинах 1440 и 390 px;
она не подтверждает перенос на развёрнутом роутере или работу продления ACME.

#### CDN-развёртывания

У каждого транспорта один протокольный шаблон и несколько CDN-развёртываний.
В каждом развёртывании отдельно задаются:

- название и CDN provider;
- distribution hostname и client SNI;
- публичный HTTPS-порт;
- origin hostname и origin TCP-порт MikroTik;
- origin TLS-профиль;
- origin-защита и флаг **Отдавать клиентам**.

Поэтому один WebSocket/XHTTP шаблон может одновременно обслуживаться через
Cloudflare с одним доменом/сертификатом и Yandex с другим. Кнопка
**Дублировать** создаёт независимую копию развёртывания.

Публичный сертификат distribution domain управляется CDN. Загружаемый в
панель TLS-профиль — сертификат участка CDN→origin или прямого HTTPS/QUIC,
смотря где он выбран. Один профиль можно переиспользовать только если его SAN
подходит всем соответствующим именам.

Внутренние Xray backend-порты (`11001`–`11004`) используются только между
Nginx и Xray в контейнере. Это не WAN-порты и не порты CDN→MikroTik. Внутренний
origin-порт может выбираться renderer, чтобы разные профили не конфликтовали;
публичный порт определяется карточкой развёртывания.

Cloudflare official CIDR обновляются атомарно. Для CDN без официального
машиночитаемого списка используется секретный `X-SB-Origin`; ручные CIDR —
расширенный fallback, а не обязательный квест.

#### Прямые подключения

Direct REALITY никогда не описывается как CDN. Настраиваются внешний адрес/
порт, SNI, handshake target/port, X25519 и Short ID. Клиентский uTLS fingerprint
настраивается в карточке удалённого пользователя; Reverse VLESS всегда
экспортируется с `Chrome`. XHTTP+REALITY дополнительно имеет полный профиль XHTTP:
packet-up/XMUX, GET uplink, размещение/ключ данных, chunk/padding/session/seq;
параметры сериализуются внутри `extra`.

Поле **Ответ без действительного ключа** появляется только когда введённый SNI
покрыт сертификатом одного из настроенных собственных TLS-профилей. Оно
переключает внешний REALITY target и локальную маскировку **API JSON**; при
выборе API подходящий TLS-профиль подставляется автоматически. Для чужого SNI
вариант API скрыт и используется внешний target. Валидный REALITY-клиент
продолжает подключаться к прежнему inbound, неизвестный SNI закрывается, а
неверный ключ на известном SNI получает нейтральный JSON 404. Режим не добавляет
WebSocket и не публикует отдельный порт. Для **gRPC + Reality** это именно
`realitySettings.target`, который принимает неавторизованный TLS-сеанс до
разбора gRPC, а не неподдерживаемый транспортом VLESS/gRPC `fallbacks`.
Локальный API объявляет ALPN `h2` и одновременно сохраняет HTTP/1.1, поэтому
маскировка отвечает правдоподобно как обычному HTTPS-, так и HTTP/2-клиенту.
TLS завершается сертификатом выбранного для транспорта профиля: отдельный
сертификат для gRPC не создаётся, но его SAN обязан покрывать настроенный SNI.

У Hysteria 2 и каждого direct REALITY-входа компактная настройка **WAN IP**
расположена рядом с **Hostname подключения**: режим **Автоматически** принимает
соединение на любом доступном WAN-адресе, а явный адрес нужен только для
раздельного использования одинакового порта на нескольких публичных IPv4.
Панель предлагает обнаруженные публичные адреса MikroTik и оставляет ручной
ввод как резерв. Список открывается поверх формы и не меняет высоту соседних
полей. REALITY `serverNames` задаются явно; сертификат
выбранного target не превращает остальные SAN в автоматически разрешённые SNI.

Переключатель **Включить транспорт** находится внизу каждой формы CDN/TLS,
REALITY и Hysteria 2. В direct XHTTP не показывается HTTP Host, потому что этот
профиль его не использует. Настройки `noGRPCHeader` и `noSSEHeader` остаются
частью XHTTP, а не gRPC-входа: они управляют HTTP-заголовками XHTTP downlink.
Поле `spiderX` располагается рядом с **PROXY protocol для fallback**. Блоки,
которые только объясняют расположение параметров в `extra` или повторяют уже
видимый выбор, отсутствуют.

В режиме внешнего target один и тот же блок **Проверить target и SNI** используется в прямых
VLESS+REALITY+Vision, VLESS+gRPC+REALITY и VLESS+XHTTP+REALITY. Панель сначала
проверяет основной SNI, цепочку сертификата, hostname, TLS и ALPN. Затем для
каждого конкретного SAN и введённого имени выполняется отдельное TLS-
рукопожатие с этим SNI. В `realitySettings.serverNames` попадают только имена,
которые получили статус **Подтверждено** и были явно отмечены. Ошибка
сертификата и отказ target принимать SNI показываются раздельно. Wildcard SAN
в конфигурацию не переносится: администратор вводит конкретное имя и проверяет
его той же кнопкой.

DNS target может вернуть IPv4 и IPv6 в одном ответе. Панель принимает проверку,
если доступный адрес завершил TLS 1.3 с нужным SNI. Адрес без маршрута
показывается предупреждением и не блокирует сохранение. Несовместимый
сертификат, отказ SNI и отсутствие `h2` у gRPC остаются блокирующими ошибками.
Если TLS не прошёл ни по одному адресу, панель не сохраняет транспорт.

В маршрутном листе переключатель **Стратегия домена** выбирает между
`IPIfNonMatch` и `AsIs`. Он влияет на клиентский Xray JSON только при включённой
индивидуальной маршрутизации. Рядом можно включить **Точечные домены**: это
редактируемый резерв к обновляемым сервисным карточкам. В Xray JSON и Mihomo
YAML выбранные карточки раскрываются в переносимые доменные/IP/port-правила без
ссылок на внешнюю геобазу. Пользовательские точечные домены получают отдельное
правило. Одинаковые домены из карточек, их зависимостей и ручного резерва
нормализуются и не повторяются внутри одного списка правил.

Пользовательское название карточки не обязано совпадать с одним серверным
набором. Панель показывает одну карточку, а генератор может объединить несколько
зависимостей и их переносимые правила. Серверные технические ID в клиентский
профиль не передаются.
Полная таблица находится в
[CLIENTS.md](CLIENTS.md#как-карточки-попадают-в-клиентский-профиль).

MAX входит в карточку **VK, Mail.ru, OK, Дзен и MAX**. Карточка явно включает
`max.ru` и другие проверенные домены экосистемы во встроенный переносимый набор.

Переключатель точечных доменов добавляет к каждой российской сервисной карточке
только её тематический поднабор из встроенного LTE-резерва SB Gateway. Полные
497 публичных суффиксов подключает только карточка **Вся зона
RU/РФ**. Несколько карточек образуют объединение без дублей. Список
пересчитывается при каждом изменении карточек; введённые администратором домены
сохраняются. Панель использует встроенный снимок и не обращается к внешней
подписке или стороннему провайдеру. Два непубличных одноуровневых имени снимок
не содержит. После сохранения список сворачивается и показывает его размер.

Карточка **FaceTime** содержит только проверенные UDP media ranges FaceTime.
Она не добавляет весь Apple `17.0.0.0/8`, iMessage/APNs, общий STUN/TURN или
правила других мессенджеров.

Один public TCP/443 нельзя одновременно назначить прямому REALITY и прямой
HTTPS-подписке на том же IP. Hysteria 2 использует UDP/443 и с TCP/443 не
конфликтует. Несколько CDN hostname, наоборот, могут делить TCP/443 через SNI
и path/service routing.

#### Адрес прямого подключения

В формах REALITY, gRPC+REALITY, XHTTP+REALITY и Hysteria 2 поле **Адрес подключения**
показывает IP/домен слева, а режим **Автоматически / Вручную** справа в одной строке,
в том числе на узком экране. Автоматический адрес доступен только для чтения;
ручной режим позволяет задать IP или домен. Переключение в авто и обратно
не стирает введённый ручной адрес.

В дополнительных параметрах Hysteria 2 режим **Проксировать сайт** принимает
фиксированный HTTPS-адрес публичного DNS-имени на порту 443. Он обслуживает
только обычные HTTP/3-запросы к UDP-входу Hysteria: TCP/443 не меняется.
Запросы идут через внутренний loopback-helper с ограничениями метода, размера,
частоты, DNS и TLS; адрес из Draft не используется до Apply. **Лимит скорости,
Мбит/с** задаёт общий payload budget helper для чтения с сайта и выдачи клиенту:
по умолчанию 1 Мбит/с, допустимо от 0,1 до 100 Мбит/с. Cookie,
authorization и Hysteria-заголовки не отправляются на сайт, а redirect и
ответные cookie не передаются клиенту. При включённом Salamander обычный
HTTP/3-клиент сайт не увидит. Это ограниченный fallback, а не полная копия
сайта и не гарантия неотличимости: фиксированный конечный HTTPS URL получает
только GET/HEAD без query, cookie и authorization. Поэтому login, динамические
JS API и переадресации могут работать не так, как у исходного сайта.
`X-Forwarded-*` доступен только у **Локального HTTP-сервиса** и не передаётся
website helper. В QUIC-блоке **Brutal без компенсации потерь** показывается
только с Brutal; **Отключить GSO** и **Отключить Stateless Reset** остаются
опциональными server-only настройками. Все три по умолчанию не сериализуются.
**UDP port hopping** также выключен по умолчанию. Укажите внешний диапазон,
случайный интервал не меньше 5 секунд и занятые UDP-порты через запятую в поле
исключений. Исключённые порты вычитаются одновременно из подписки и RouterOS NAT.
Конфликт с существующим чужим dstnat или WireGuard listen-port останавливает Apply
до изменения RouterOS. Допустимо не более 1001 порта в исходном диапазоне.
Проверка читает фактические правила RouterOS заново при каждом Apply; список
исключений может образовать не более 64 управляемых диапазонов.
У пустого **Минимальная версия клиента** REALITY нет скрытого порога:
подсказка **Без ограничения версии** означает официальное поведение Xray 26.9.9.
Предел body 2 MiB остаётся защитным максимумом, но не обещает загрузку такого
ответа: общий 15-секундный deadline и общий бюджет обоих hop могут остановить
ответ раньше. Лимит относится к payload fallback, а не к wire-rate, QUIC
handshake или авторизованному VPN-трафику.

Рекомендуемый и начальный профиль Hysteria использует `congestion=bbr`,
`keepAlivePeriod=15`, `udpIdleTimeout=60`, включённые PMTU/GSO/Stateless Reset
и выключенный Salamander. **API JSON** выбран как masquerade по умолчанию:
неавторизованный обычный HTTP/3-запрос получает нейтральный JSON, тогда как
валидный Hysteria-клиент проходит обычную проверку пароля.
Основной выбор masquerade занимает одну колонку формы на desktop и переходит на
полную ширину только вместе со всей сеткой на узком экране.
Локальная регрессия использует синтетический HTTPS-origin и не обращается к
выбранному стороннему сайту; она не заменяет проверку реального HTTP/3-потока
на RouterOS.

Новые прямые транспорты используют автоматический режим; существующий hostname
без `hostname_mode` остаётся ручным, чтобы не заменить заданный пользователем домен.
Для перехода существующего транспорта выберите автоматический режим, сохраните и примените.

Автоматический адрес — единственный IPv4 интерфейса из списка WAN, через который
идёт активный маршрут `0.0.0.0/0` таблицы `main`. Частный адрес допустим для
подключения внутри сети вышестоящего роутера. Это не определение внешнего адреса
за NAT: для внешнего подключения через вышестоящий NAT нужны его проброс портов
и ручной публичный IP/DDNS. Сеть управления и policy/VPN-маршруты не используются.
При нескольких подходящих IP/интерфейсах или недоступности RouterOS автоматический
адрес не угадывается: панель сообщает проблему, экспорт не выдаёт старый IP.

Панель, клиентские URI/Xray/sing-box/Mihomo, ZIP и reverse-конфиги используют один источник.
Кеш содержит один снимок на 30 секунд, включая неудачный результат; параллельные
запросы не запускают повторные проверки. Панель получает изменения с обычным
минутным обновлением overview (до 90 секунд с учётом кеша), без перезагрузки страницы.
Текущий IP не записывается в Draft, не меняет ревизию и не перезапускает Xray.
Скачанные ранее статические конфиги нужно скачать заново; подписку — обновить в клиенте.

Блок **Привязка входящего порта** удалён из формы. При сохранении Go-сервер
сам определяет `wan_destination_address`: ручной IP, точно совпавший с IPv4
на включённом WAN-интерфейсе MikroTik, становится также привязкой NAT.
Учитываются второй адрес того же интерфейса и адрес резервного WAN без активного
default route; адреса управления, выключенные и invalid адреса не подходят.
Ручной внешний IP/домен и режим **Автоматически** очищают фиксированную привязку.
Домен не разрешается через DNS для определения принадлежности роутеру.
Если снимок WAN получить не удалось, сохранение ручного IPv4 отклоняется без
изменения черновика. Список своих IP предлагается в ручном поле без новых подсказок.
Браузер не задаёт NAT-привязку самостоятельно. Она начинает действовать после Apply,
не после одного Save. Разрешённые входящие интерфейсы, SNI, target, TLS и ключи
от выбора адреса не меняются. Имеющиеся конфиги не переписываются при чтении;
новая логика действует при сохранении транспорта с явным `hostname_mode`.

При публикации через белый IP другого роутера и WireGuard клиенту нужен ручной
белый IP/домен. Проброс на локальный IP RouterOS сам по себе недостаточен:
штатный прямой dstnat принимает вход только из списка WAN. Нужны отдельные узкие
правила перенаправления и разрешения нужного порта через WG, а также обратный путь через тот же туннель
(например, ограниченный SNAT на публикующем роутере или согласованная policy routing).
Форма сама такой проброс не создаёт и не добавляет WG-интерфейс целиком в WAN.
Сохранение уже включённого REALITY-транспорта с прежними target, портом, SNI и
списком дополнительных SNI не запускает повторную сетевую проверку target.
Новый/включаемый транспорт или изменение этих параметров требует проверки;
кнопка ручной проверки остаётся доступной.
Индикатор «Применено» и кнопка Apply используют сводку только для текущей ревизии
черновика. После сохранения новая ревизия и её счётчики имеют приоритет над старой
минутной сводкой; дополнительного опроса RouterOS для этого не требуется.

#### Сброс параметров транспорта

Один компактный блок **Сброс и пересоздание** доступен во всех восьми
формах транспорта: WebSocket+TLS, gRPC+TLS, HTTPUpgrade+TLS, XHTTP+TLS,
VLESS+REALITY+Vision, VLESS+gRPC+REALITY, VLESS+XHTTP+REALITY и Hysteria 2.
Единая кнопка **Сбросить** открывает общий список базовых параметров и доступных
ротаций. После выбора она становится зелёной, показывает количество действий,
а строка под заголовком перечисляет их до сохранения. Клик вне меню и `Escape`
закрывают popover без потери выбора. Выбор **Базовые параметры** сразу заполняет
совместимые значения, включая поля в закрытых блоках; снятие пункта возвращает
состояние формы до выбора. Это не проверка сети. Draft изменится лишь после
**Сохранить изменения**, а действующая конфигурация — после Apply.

Сброс никогда не придумывает и не меняет домены, SNI/REALITY target,
WAN IP, внешние и внутренние порты, сертификаты, private key, секретные path и
service name, состояние транспорта или флаги ротации ключей. Все экспертные
поля остаются доступны в своих disclosure-блоках; готовый набор лишь заполняет
совместимые безопасные значения транспорта. После сохранения выполняется тот
же полный preflight, что и при ручном вводе.

Ротация секретов не занимает отдельные строки или вторую кнопку. Общее меню
показывает только применимые к текущему транспорту значения: HTTP path, VLESS
Encryption, имя gRPC, X25519/Short ID, ML-DSA-65 и пароль Salamander. Выбранные
пункты пересоздаются только после **Сохранить изменения** и Apply. Ручное поле
имени gRPC удалено: существующее секретное имя сохраняется, а новое создаётся
через это меню.

Новая Hysteria-конфигурация получает QUIC keepalive 15 секунд: это поддерживает
UDP-состояние мобильного NAT при простое. Администратор может выбрать 2–60 секунд
или очистить поле, чтобы отключить keepalive. Необязательные `max idle` и
`max incoming streams` показываются пустыми, когда в конфигурации хранится
нулевое значение Xray; пустое поле снова сериализуется как `0`.

В блоке **Качество узлов** кнопка с часами после периода **30 дней** начинает
новое видимое окно для выбранного маршрутного листа и сразу включает **24 часа**.
Она не удаляет историю health-agent и не влияет на автоматический выбор узла:
панель локально скрывает старые замеры, пока не накопятся новые. Повторное нажатие
возвращает полные 24 часа. Отсчёт хранится отдельно для каждого листа в браузере.
На компактной ширине номера листов, периоды и кнопка нового отсчёта сохраняют
одну строку и одинаковую высоту; длинный список номеров прокручивается внутри
своей группы, не перенося остальные элементы вниз.

#### HTTPS-ссылка клиентской подписки

Подписка имеет имя в клиентском приложении (по умолчанию `SB Gateway`) и
непрозрачный 256+ bit path без слов `sub`, `subscription` или `links`.
Доступны три режима:

1. **Через CDN** — отдельный CDN endpoint хранит два разных имени: **Домен
   раздачи CDN** остаётся публичным адресом ссылки, а **DNS-имя origin** —
   SNI/Host CDN → шлюз. Это не адрес подключения CDN и панель не создаёт DNS
   запись. **Публичный HTTPS-порт** используется в URL клиента на стороне CDN,
   а **TCP-порт origin на MikroTik** — только для соединения CDN → шлюз и
   фактического listener Nginx/правила RouterOS. Поэтому схема `443 → 18443`
   задаётся без подмены клиентского URL. Во второй строке сначала выбирается TLS-профиль origin, затем его
   DNS-имя. Единственный concrete SAN подставляется, а при нескольких SAN поле остаётся обычным ручным input с
   datalist. Готовое CDN-развёртывание по-прежнему не создаёт новый WAN-порт
   или маршрут;
2. **Напрямую** — DNS указывает на WAN MikroTik, выбранный TCP-порт реально
   занимает direct endpoint;
3. **Два адреса** — CDN и прямой URL работают параллельно; основной задаёт порядок
   и значение для обратной совместимости. Уже настроенный отдельный CDN-домен
   остаётся доступен в списке и не смешивается с прямым DNS-именем: его edge-домен
   сохраняется отдельно, а прямым адресом становится существующее DNS-имя origin.
   В качестве CDN по-прежнему можно выбрать готовое развёртывание транспорта.

Несколько CDN-подключений и подписка могут использовать один публичный 443,
только если у них одинаковая RouterOS-граница источников. Cloudflare-only,
ручные CIDR и открытый/secret-header origin нельзя смешивать на одном
origin-порту: Check потребует общий режим защиты либо другой порт, чтобы более
широкое правило не открыло соседний virtual host.
У configured отдельного CDN endpoint origin обязателен, должен быть concrete
DNS-именем и не подменяется публичным edge-доменом. Неполный Draft можно
сохранить для дальнейшего редактирования, но Check/Apply и runtime render его
не принимают. Смена origin TLS-профиля заменяет origin единственным SAN; edge
никогда не меняется этим действием.
Переключение **Через CDN → Напрямую** не переносит edge-домен в поле прямого
адреса. Панель подставляет сохранённое DNS-имя origin, а при возврате к CDN
показывает ранее настроенный edge-домен вместо фиктивного нового развёртывания.
Переключатель **Публикация подписки** выключает только выдачу HTTPS-подписки.
Адреса, TLS-профиль и защита origin остаются в форме без изменений; пока
переключатель выключен, их не нужно заполнять и кнопка DNS/TLS-проверки
недоступна.
Кнопка **Проверить DNS и TLS** проверяет выбранную схему до сохранения.
В открытом окне остаются только имя и поля выбранного способа публикации. Порт,
защита origin, срок прежнего URL и выбор основного адреса находятся в
**Дополнительно**. Заголовок и нижние действия не прокручиваются вместе с
формой; при каждом открытии тело окна начинается сверху.
Порты разделяются для любого выбранного CDN, а не только для Cloudflare или
Gcore. Для Cloudflare панель дополнительно ограничивает только публичный edge
его документированным набором HTTPS-портов; origin-порт остаётся независимым.
В окне ссылки удалённого пользователя оба URL режима **Два адреса** всегда
показываются одновременно как **CDN-ссылка** и **Прямая ссылка**. У каждой строки
собственная кнопка копирования.

В настройках удалённого пользователя выбирается формат подписки: совместимый
режим, JSON-массив, Xray JSON, sing-box JSON, Mihomo YAML либо URI/base64 только с узлами. Сохранённый
выбор применяется к секретному URL без дополнительных параметров; явные
`?format=links`, `?format=array`, `?format=xray`, `?format=singbox` и
`?format=mihomo` имеют приоритет. Фактический
формат указан в `X-SB-Profile-Format`. Рекомендуемый совместимый режим сохраняет
обычный URI/base64-список для неизвестных приложений независимо от общего
`Accept: application/json`. При включённых функциях полного профиля Happ,
v2rayNG и V2Box получают JSON-массив отдельных транспортов и дополнительного
автовыбора, причём автовыбор расположен первым. Экспортируемые клиентские
Xray JSON, sing-box JSON и Mihomo YAML не ссылаются на серверные `geosite:*`: выбранные
карточки разворачиваются в нормализованный список переносимых доменов без
повторов. **Индивидуальная маршрутизация** и дополняющие её **Точечные домены**
включаются только вручную; выбор карточки не меняет эти настройки.
В этом app-managed JSON DNS содержит только переносимые resolver `8.8.8.8` и
`1.1.1.1`, а домены — только нормализованные `routing.rules` без повторов.
Для совместимости embedded-ядер транспорт записывается через `network`, а
выбранный у пользователя fingerprint передаётся его поддерживаемым узлам без
скрытой подмены.
Полный направленный DNS detour остаётся в одиночных Xray, sing-box и Mihomo-профилях.
Hiddify/Karing/sing-box получают нативный sing-box JSON; его сервисные домены
не дублируются в DNS, а имена transport-узлов используют прямой bootstrap DNS.
Одиночные Xray, sing-box и Mihomo-профили выдаются только при явном выборе
либо уверенном определении соответствующего ядра по `User-Agent`.
Поддержку конкретного транспорта и дополнительных параметров нужно проверять
в используемой версии приложения; название ОС не определяет возможности ядра.

| Дополнительные WS/HTTPUpgrade HTTP-заголовки | HTTP 422, без неполного профиля | Да | Да | Да |
| HTTPUpgrade | `type=httpupgrade` | `httpupgradeSettings` | `transport.type=httpupgrade` | `network=ws`, `v2ray-http-upgrade=true` |
| XHTTP headers / noGRPCHeader | В `extra`, поддержка зависит от импортёра | Да | Да, через `xray_outbound_raw` | Да |
| Отдельный XHTTP downloadSettings | В `extra`, поддержка зависит от импортёра | Да | Да, через `xray_outbound_raw` | HTTP 422: перенос отдельного StreamConfig не реализован |
| TCP sockopt, расширенные gRPC параметры, ML-DSA verify | Только поддерживаемые URI-поля | Да; TCP timeout зависит от ОС | Поддерживаемая sing-box часть | Xray-only параметры не переносятся |

HTTP 422 означает несовместимость выбранного формата с настройками, а не
отсутствие пользователя. Серверные настройки при экспорте не изменяются.
Чтобы использовать обычную ссылку, дополнительные WS/HTTPUpgrade заголовки
должны оставаться пустыми (Host передаётся штатно).

REALITY public key для клиентских ссылок всегда выводится из активного private
key в SecretStore. Поэтому ротация ключа не требует ручной синхронизации
производного поля и не оставляет XHTTP/Vision/gRPC профиль со старым ключом.

В полном Xray-профиле выбор VPN DNS DoT преобразуется в DoH **того же
провайдера**: встроенный DNS Xray не поддерживает `tls://`. Теги и направление
запросов сохраняются для обоих режимов WAN/VLESS. На самом шлюзе и в Mihomo
выбранный DoT не меняется. Это адаптация формата, не откат к открытому DNS.

Источники форматов: [Mihomo VLESS](https://github.com/MetaCubeX/mihomo/blob/Meta/adapter/outbound/vless.go),
[Mihomo WebSocket/HTTPUpgrade](https://github.com/MetaCubeX/mihomo/blob/Meta/transport/vmess/websocket.go),
[Xray DNS](https://github.com/XTLS/Xray-core/blob/main/app/dns/nameserver.go),
[Happ — импорт профилей](https://github.com/HappDev/happ_su/blob/main/dev-docs/examples-of-links-and-parameters.md),
[v2rayNG — несколько JSON-конфигураций](https://github.com/2dust/v2rayNG/issues/3852),
[V2Box — журнал поддержки JSON-массивов](https://apps.apple.com/us/app/v2box-v2ray-client/id6446814690).

В дополнительных настройках публичной ссылки можно указать общий Happ Provider
ID. Идентификатор берётся из аккаунта провайдера Happ и не генерируется
панелью. В карточке каждого удалённого пользователя после этого становятся
доступны три параметра iOS: `Include all networks`, `Exclude local networks` и
`Exclude APNs`. Компактная секция **Happ на iOS · системный туннель** по
умолчанию свёрнута; все три параметра включены по умолчанию. Они передаются
только по ссылке этого пользователя и только при настроенном Provider ID; без
него секция раскрывается с недоступными параметрами и объясняет причину, а
значения нужно выставить вручную в Happ.

Раздельное хранение в панели позволяет выдавать разные значения разным
пользователям. В самом Happ эти флаги относятся к глобальному системному
туннелю приложения, поэтому на устройстве с несколькими подписками последняя
обновившаяся подписка имеет приоритет. Для JSON-массива с доступом к удалённому
LAN панель также включает Xray TUN и очищает прежние excluded routes до
loopback. Исключение APNs оставляет системные push-уведомления iOS вне полного
туннеля, а `Exclude local networks` сохраняет AirPlay, AirDrop и CarPlay в
текущей локальной сети устройства.

Только форма удалённого VLESS-пользователя содержит флаг **Индивидуальная
маршрутизация**. Без него весь публичный трафик отправляется на SB Gateway; при
включении правила выбранного листа попадают в полный Xray/sing-box/Mihomo-профиль.
LAN-, WireGuard- и OpenVPN-клиенты всегда исполняют лист на шлюзе. Карточка
маршрутного листа показывает компактные счётчики обоих режимов без раздельных
групп и без дублирования самого листа.

Блок **Полный профиль** включает индивидуальную маршрутизацию, автоматический
выбор узла и консервативный AdBlock. Локальная Wi-Fi/LAN сеть устройства всегда
сохраняется и не показывается отдельной настройкой. Доступ к LAN остаётся
серверным ограничением: профиль не может выдать `internet-only` доступ к
внутренним сетям MikroTik.

### Эксплуатация

Содержит диагностику, зашифрованные recovery archives, update, rollback и
full uninstall. В карточке фактического состояния невыполненная проверка
показывает локализованную причину отдельной строкой под названием проверки;
длинная причина переносится внутри карточки и не пересекается с соседними
строками или итоговым статусом.

#### Резервные копии

`.sbgw` шифруется текущим паролем панели. Отдельного backup password нет.
Панель обязательно хранит до трёх архивов на внешнем SSD. До трёх зеркал в
RouterOS Files создаются асинхронно по принципу best effort: их временная
недоступность не блокирует update/restore. Доступны **Создать**, **Скачать**,
загрузка `.sbgw` из браузера и **Восстановить**. Restore спрашивает пароль для
расшифровки; архив не содержит пароль или действующие сессии.

#### Обновление контейнера

Строка **Обновление контейнера** открывает modal с явным browser file input.
Нужен один Docker `.tar`. Панель проверяет SB Gateway, `linux/arm64`, SHA-256 и
версию; второй tar и `.sha256` не нужны. До отправки body выполняется короткая
preflight-проверка внешнего SSD; если каталог проекта не задан или недоступен
для записи, форма сразу показывает действие для исправления, а архив не
загружается. Во время записи видны процент и переданные/общие байты.

После одной галочки RouterOS переводит
маршрутизацию в fail-open, держит прежний контейнер остановленным на probation
и автоматически возвращает его при ошибке. После успеха временные объекты и
rollback container удаляются. Отдельный progress-dialog показывает версию,
таймер, подготовку RouterOS, переключение и health/probation. Он считает
перезапуск панели ожидаемым, автоматически восстанавливает опрос и показывает
финальный успех, остановку до переключения либо выполненный rollback. Активная
операция снова открывает этот диалог после обновления страницы.

Строка **Журналы SB Gateway** открывает единый просмотр последних 300 строк
Xray error/process, control plane, nginx и событий обновления. Все источники
заданы сервером; произвольный путь к файлу передать нельзя. Управление уровнем
логирования доступно только на вкладках Xray.

#### Полное удаление

Modal сначала показывает **Будет удалено** и **Будет сохранено**. Одна галочка
разрешает удалить только подтверждённый project storage root и точные
RouterOS-объекты `SB-GATEWAY`. Чужие firewall/routes/VPN/files не затрагиваются.
После завершения не должно оставаться контейнеров, mount/env/veth/scheduler и
управляемых backup/upload хвостов.

### Настройки

Содержит доступ к панели, CSRF/secret safeguards, параметры Xray/сети,
connection guard, лимиты ресурсов и явную компактную форму **Сменить пароль**.
Интерфейс показывает названия параметров, текущие значения и ошибки без
повторяющих их технических пояснений. Краткая подсказка остаётся только там, где
нужно задать формат списка: один IP/CIDR или один интерфейс на строку.
Единственная основная кнопка **Сохранить изменения** расположена после последней
карточки настроек; на телефоне она занимает всю ширину.
Для Xray показываются только совместимые настройки; sing-box и его поля в
интерфейсе отсутствуют.

Connection guard касается только новых WAN-соединений к фактически
опубликованным портам SB Gateway. Он не затрагивает другие порты MikroTik,
management/LAN, established/related и доверенные origin CIDR.

## Аварийный путь

Если панель работает: **Эксплуатация → резервная копия/rollback**. Если панель
не работает: локальный WebFig → Containers/Logs и project-owned recovery
script. Статический `sb-gateway` допустим только в локальной shell контейнера. Ручное
удаление таблиц RouterOS целиком запрещено.
