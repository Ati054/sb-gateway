# Клиенты, подписки и маршрутизация

Документ соответствует SB Gateway 1.6.18. Все штатные операции выполняются в
Web UI; YAML и SecretStore вручную редактируются только при восстановлении.

## Два вида подписок

Не смешивайте:

- **провайдерскую подписку** — входной URL, из которого SB Gateway получает
  внешние VLESS/Hysteria 2 узлы для исходящего трафика;
- **клиентскую подписку SB Gateway** — выходной HTTPS URL, который iPhone или
  другое приложение получает от шлюза и в котором перечислены включённые
  серверные входы SB Gateway.

Провайдерский URL хранится в SecretStore и полностью показывается только
авторизованному администратору в форме настройки подписки. Он не маскируется
точками, длинное значение можно прокрутить по горизонтали, но URL не
дублируется в журнале и в общем списке. При разборе URI
технические параметры берутся из самой ссылки, а имя узла сохраняется как в
подписке, включая emoji и пунктуацию. Текстовое описание технологии не
считается доказательством protocol/SNI/CDN.

Если провайдер выбирает формат ответа по `User-Agent`, control plane сначала
использует собственный идентификатор, а при неподдерживаемом документе
автоматически повторяет запрос как v2rayNG и Clash Meta. Ручная настройка для
этого не требуется.

Клиентская подписка имеет изменяемое имя в приложении (`SB Gateway` по
умолчанию), непрозрачный path и может выдаваться через CDN, напрямую или по
двум адресам. Подробности — в [WEB-UI.md](WEB-UI.md).

## Локальный или VPN-клиент

В **Устройства → Добавить устройство** задаются:

1. имя устройства;
2. точный source `/32`, действительно нужная подсеть либо общий охват LAN/Wi-Fi;
3. тип: LAN/Wi-Fi, WireGuard, OpenVPN или другой routed VPN;
4. маршрутный лист и service routes;
5. режим `VLESS + WAN` или `WAN + VLESS`;
6. сервисы-исключения из доверенного каталога;
7. поведение при отказе контейнера: обычный WAN или только LAN.

Для источника **LAN / Wi‑Fi MikroTik** панель показывает только DHCP-аренды,
которые администратор перевёл в `Make Static`. Динамические Active Hosts не
добавляются в список. Название строки выбирается в порядке: комментарий
статической аренды, `host-name`, сообщённый DHCP-клиентом, затем MAC/IP.

Переключатель **Все устройства LAN / Wi‑Fi** создаёт одну общую запись для
IPv4-подсетей интерфейсов, включённых в стандартный список RouterOS `LAN`.
Поэтому статические и динамические DHCP-адреса внутри этих подсетей получают
выбранный маршрут без отдельных карточек и без обновления после каждой смены
адреса. Новую LAN-подсеть нужно один раз прочитать кнопкой **Обновить список**,
сохранить и применить. Общая запись может быть только одна. Если для конкретного
адреса создана отдельная включённая карточка, её маршрутизация и DNS проверяются
раньше общего правила и полностью определяют поведение этого устройства.

Маршрут работает так:

| Режим | Обычный публичный трафик | Выбранные сервисные карточки |
|---|---|---|
| `VLESS + WAN` | выбранная VPN-политика | WAN |
| `WAN + VLESS` | WAN | выбранная VPN-политика |

При пустом списке сервисов исключений нет. Новые сервисы добавляются поиском по
имени, домену или URL только из доверенного полного service pack
[`v2fly/domain-list-community`](https://github.com/v2fly/domain-list-community).
Recursive includes разворачиваются до полного набора сайта, API, WebSocket и
CDN-зависимостей; ошибочный ответ не заменяет LKG. Технический ID
маршрутного листа создаётся автоматически и не показывается пользователю;
назначение выполняется по полю **Название маршрута**. Совместимые старые
`direct_domains`
сохраняются при редактировании. Корневое имя включает поддомены. Приложение с
жёстко заданным IP, DoH/ECH или неизвестным CDN endpoint требует отдельной
проверки. TCP/UDP DNS 53 управляемого клиента перехватывается: WAN использует
свой resolver, а VPN — отдельный DoH/DoT resolver, upstream-соединение которого
идёт через тот же VLESS, Reverse VLESS или WireGuard selector. Параллельно
проверяйте отсутствие DNS leak.

Карточки сервисов используют одну симметричную семантику: в `VLESS + WAN` они
идут через WAN, в `WAN + VLESS` — через выбранную VPN-политику. Отдельное
всегда-прямое исключение сохраняется только для BitTorrent при включённой
настройке **Torrent через WAN**. Тот же результат формируют серверный runtime,
симуляция маршрута в панели и индивидуальные Xray/sing-box/Mihomo-профили; выключенный
переключатель возвращает BitTorrent к обычной семантике сервисной карточки.

Устройство вне `SB_MANAGED_CLIENTS` не направляется в контейнер. Внутренние
назначения всегда исключаются до policy routing и остаются в RouterOS main.

Для WireGuard источником клиента является **peer**, а не интерфейс. Один общий
WireGuard-интерфейс может обслуживать любое число независимо маршрутизируемых
клиентов. Панель показывает одну строку на peer, использует его имя как основную
подпись и объединяет все принадлежащие ему конкретные IPv4-префиксы в одну
запись. `/32` используется для обычного клиента, сеть — для site-to-site peer,
а `0.0.0.0/0` источником клиента не считается. Интерфейс выводится только
справочно. Стабильная ссылка на RouterOS peer
сохраняется вместе с клиентом, поэтому изменение его `allowed-address` не
создаёт вторую карточку и при следующем открытии формы заменяет прежний source
CIDR актуальным. Перед Check, Plan и Apply ссылка повторно разрешается по live-
инвентарю RouterOS: старый CIDR заменяется текущими префиксами, а удалённый и заново
созданный peer требует явного повторного выбора и не может незаметно получить
правила прежнего клиента. Маршрутные подсети вроде `0.0.0.0/0` или
`192.168.0.0/16` не считаются идентификатором клиента.

## Удалённый пользователь SB Gateway

В **Устройства → Добавить пользователя** задаются имя подключения, доступ к LAN,
маршрутный лист, client TUN CIDR и серверные транспорты. UUID создаётся control
plane и хранится в SecretStore. Один remote user не получает обычный WAN как
неявный fallback.

| Доступ к LAN | Внутренние сети | Публичный интернет |
|---|---|---|
| `trusted-full` | актуальные private IPv4-маршруты из live RouterOS | назначенный маршрутный лист |
| `trusted-limited` | только CIDR/ports | назначенный маршрутный лист |
| `internet-only` | reject | назначенный маршрутный лист |
| `disabled` | авторизация запрещена | запрещён |

`client_tun_address` обязателен для включённого remote user. Выберите свободный
IPv4 host/CIDR с пригодным адресом и префиксом `/30` или шире, который не
пересекается с сетями клиентского устройства. Скрытого fallback нет.

Для `trusted-full` control plane каждые 30 секунд читает полный live-инвентарь
маршрутов RouterOS и сохраняет только последний успешно завершённый снимок.
Добавленный или удалённый RFC1918-маршрут не требует входа в панель и Apply:
обновлённый точный CIDR-набор попадёт в следующий запрос клиентской подписки.
Служебные container/TUN link-сети исключаются. При временной недоступности
RouterOS сохраняется последний рабочий снимок, а не публикуется пустой профиль.
`trusted-limited` по-прежнему расширяется только явным выбором администратора.
Публичный endpoint запрещает хранение ответа в CDN и объявляет зависимость от
`User-Agent` и `Accept`: одна ссылка может корректно выдавать разные форматы
разным приложениям. После изменения live-маршрутов клиент всё равно должен
выполнить очередное обновление подписки; Apply на шлюзе для этого не нужен.

В автоматическом режиме новые включённые server transports появляются в
подписке пользователя после Apply. При ручном режиме набор выбирается
галочками. В компактной карточке показывается только число узлов; технические
IDs не выдаются как пользовательские названия.

Поле **uTLS fingerprint** принадлежит удалённому пользователю, а не серверному
транспорту. По умолчанию используется `Chrome`; отдельному пользователю можно
выбрать Chrome, Firefox, Safari, iOS, Android, Edge, 360, QQ или случайный
известный профиль. Один выбор применяется ко всем его VLESS/REALITY и Hysteria 2
узлам в форматах, где клиент поддерживает имитацию ClientHello. Серверные
inbound-параметры от этого не меняются.

Только у удалённого VLESS-пользователя есть флаг **Индивидуальная
маршрутизация**. Без него весь публичный трафик сначала приходит в SB Gateway,
где назначенный маршрутный лист применяет режим WAN/VLESS, карточки и DNS. При
включении Xray JSON или Mihomo YAML получает правила того же листа и выполняет
их до сервера. URI/base64 содержит только узлы, поэтому при таком импорте
правила по-прежнему исполняются на шлюзе.

LAN-, WireGuard- и OpenVPN-клиенты всегда исполняют маршрутный лист на шлюзе;
отдельного переключателя у них нет. Один и тот же лист можно назначать смешанному
набору клиентов без копирования правил.

Остальные параметры блока **Полный профиль** управляют содержимым JSON/YAML:

- **Автоматический выбор узла** создаёт health-based fallback между выданными
  транспортами. Он не добавляет WAN fallback удалённому пользователю.
- **Блокировка рекламы** включает небольшой консервативный список рекламных и
  аналитических доменов. Это не заменяет полноценный обновляемый фильтр.
Частные адреса текущей Wi-Fi/LAN сети остаются прямыми и отдельного
переключателя для этого нет. Явно разрешённые доступом к LAN сети MikroTik
вырезаются из широких private `DIRECT`-диапазонов и идут через SB Gateway;
результат не зависит от порядка правил в клиентском ядре. Это не расширяет доступ:
`internet-only` по-прежнему не получает доступ к LAN MikroTik.

Happ на iOS/Android окружает Xray собственным системным туннелем. Для
автоматического управления этим туннелем Happ требует зарегистрированный
`Provider ID`: его можно указать в **Подключения → Ссылка подписки →
Дополнительно**. Идентификатор общий для издателя подписки, а значения
`Include all networks`, `Exclude local networks` и `Exclude APNs` задаются в
карточке каждого удалённого пользователя. По умолчанию включены все три:
интернет идёт через VPN, устройства текущей локальной сети iPhone остаются
доступны напрямую, а APNs не теряет фоновые push-уведомления.

Панель передаёт эти три значения в ответе конкретной ссылки только вместе с
Provider ID. При этом Happ применяет их как глобальные настройки своего
системного туннеля: если на одном устройстве есть несколько подписок с разными
значениями, приоритет получает последняя обновившаяся подписка. Для полного
JSON-профиля с удалённым LAN панель дополнительно включает Xray TUN и заменяет
старые `excluded routes` только loopback-диапазонами. Без Provider ID параметры
нужно один раз выставить вручную в DevSettings приложения. Серверный JSON
routing от Provider ID не зависит. Эти HTTP-заголовки выдаются только Happ;
Streisand, Shadowrocket, Hiddify, v2rayTun и остальные клиенты не получают их.

Provider ID не является секретом: он передаётся клиенту в HTTP-заголовке.
Однако Happ связывает его с аккаунтом и доменом подписки, поэтому панель не
создаёт фиктивный ID и не заимствует идентификатор другой подписки. Общий
Xray/sing-box/Mihomo-профиль использует то же непересекающееся разбиение на всех
поддерживаемых платформах и от Happ Provider ID не зависит.

### Как карточки попадают в клиентский профиль

SB Gateway не передаёт содержимое `geosite.dat` внутри подписки. Поэтому полный
Xray JSON, sing-box JSON и Mihomo YAML самодостаточны: они содержат встроенные fallback-домены
карточек и выбранные точечные домены, но не содержат внешних ссылок `geosite:*`, отсутствие
которых может полностью остановить мобильное ядро. URI/base64-набор содержит
только узлы и не переносит индивидуальную маршрутизацию.

Генератор раскрывает российские карточки так:

| Карточка в панели | Серверные источники каталога | Переносимые домены в полном профиле |
|---|---|---|
| Госуслуги и государственные сайты | `category-gov-ru` | проверенные критические домены |
| Банки и платежи РФ | `category-bank-ru` | НСПК, СБП и проверенные домены банков |
| Маркетплейсы, объявления, доставка и ритейл РФ | `category-ecommerce-ru`, `ozon`, `category-retail-ru` | службы доставки и проверенные домены |
| Экосистема Яндекса | `yandex` | проверенные домены и CDN |
| VK, Mail.ru, OK, Дзен и MAX | `mailru-group` | проверенные домены и CDN; upstream `mailru-group` включает MAX |
| Транспорт и путешествия РФ | `category-travel-ru` | проверенные транспортные домены |
| Мобильные операторы и провайдеры связи РФ | `megafon`, `mts-ru`, `rostelecom`, `t2-ru` | Beeline, Дом.ру и другие проверенные домены |
| Медиа, ТВ, видеостриминг и музыка РФ | `category-media-ru`, `category-entertainment-ru` | онлайн-кинотеатры, музыка и проверенные CDN |
| Образование, работа и ИТ-сервисы РФ | `category-education-ru`, `category-tech-media-ru` | вакансии, облака, хостинг и проверенные домены |
| Вся зона RU/РФ | `category-ru` | полный встроенный LTE-резерв |

Названия карточек служат пользовательскими группами. Для клиентских Xray,
sing-box и Mihomo генератор обходит зависимости карточки, раскрывает их в
переносимый встроенный список доменов и удаляет повторы. Экспортируемый профиль
не зависит от конкретных секций `geosite.dat` стороннего приложения.

Переключатель **Точечные домены** вручную подключает полный тематический
LTE-резерв и дополняет индивидуальную маршрутизацию. Выбор карточки не включает
ни его, ни **Индивидуальную маршрутизацию** автоматически:

| Карточка | Доменов в локальном снимке |
|---|---:|
| Госуслуги | 131 |
| Банки | 69 |
| Маркетплейсы и ритейл | 50 |
| Яндекс | 57 |
| VK/Mail.ru/MAX | 58 |
| Транспорт | 29 |
| Операторы связи | 13 |
| Медиа | 27 |
| Образование и ИТ | 63 |

Эти девять поднаборов содержат 497 уникальных публичных доменных суффиксов.
Карточка **Вся зона RU/РФ** подключает весь снимок. Несколько тематических
карточек образуют объединение без дублей. Панель пересчитывает автоматическую
часть после выбора или снятия карточки и сохраняет домены, введённые вручную.
Локальный снимок не зависит от внешней подписки и не заменяет `geosite`.

## Reverse VLESS как исходящий узел

Reverse-клиент — отдельный Xray-клиент, подключающийся к одному или нескольким
включённым direct server inbounds и предоставляющий шлюзу самостоятельный
internet egress. В карточке выбираются REALITY, gRPC+REALITY и/или
XHTTP+REALITY; один UUID используется как пул соединений.
Обычные WebSocket, gRPC+TLS, HTTPUpgrade и XHTTP+TLS не являются reverse
транспортами и не принимаются ни формой, ни API, ни экспортером.

Кнопка скачивания выдаёт готовую Xray-конфигурацию reverse-клиента. После
реального подключения узел участвует в health, рейтинге, приоритете и failover.
Наличие формы и успешный config test не доказывают egress: end-to-end трафик и
нагрузка проверяются с Raspberry Pi или VPS.

Серверный контейнер использует Xray-core 26.9.9; скачиваемый удалённый reverse
bridge остаётся закреплён на 26.7.28. Header экспорта сообщает bridge-версию.
Экспорт использует стабильный `streamSettings.network`, поэтому уже установленный
reverse JSON не требуется скачивать заново только из-за обновления серверного
ядра. Повторное скачивание нужно при изменении адреса, секрета, транспорта или
других параметров самого профиля.
Все Reverse VLESS bridge-профили получают фиксированный fingerprint `Chrome`:
это нейтральный массовый ClientHello и он не зависит от Linux/OpenWrt/Windows на
reverse-хосте.
Экспорт содержит стабильные поля `network` и `streamSettings.method`, поэтому
обновление серверного ядра не требует повторной настройки reverse-host.
Состояние `online` и успешный config test сами по себе недостаточны: поддержку
этой пары подтверждает сквозная проверка публичного трафика через каждый
выбранный Reverse VLESS transport.

Экспорт самодостаточен и не требует `geoip.dat`: `finalRules` сначала блокируют
приватные и резервные диапазоны, затем разрешают публичный internet egress.
После изменения серверных входов, состава пула или обновления формата экспорта
скачайте JSON заново, замените файл на reverse-host и перезапустите закреплённый Xray 26.7.28. Статус
`online` подтверждает управляющее reverse-соединение, но не актуальность
`finalRules` в уже запущенном на Raspberry Pi старом файле.

## WireGuard MikroTik как исходящий узел

В **Маршрутизация → Дополнительные выходы** панель показывает только включённые
WireGuard-интерфейсы RouterOS с однозначно выбранным peer. Для входящих
клиентов действует другая модель: один peer — один клиент, поэтому в карточке
устройства главным именем является имя peer, а интерфейс показан справочно.

Пользователь не добавляет `0.0.0.0/0` и default route вручную. После выбора и
Apply SB Gateway:

- сохраняет исходный `allowed-address` peer и добавляет full-tunnel prefix;
- создаёт отдельную `sb-wg-*` routing table и source rule только для Xray;
- не меняет default route в `main`, поэтому сам MikroTik и остальные клиенты
  продолжают использовать прежнюю маршрутизацию;
- удаляет project-owned правила и возвращает исходный peer при снятии выбора.

WireGuard-выход участвует в health, рейтинге, `best`/`priority` и failover на
тех же правах, что VLESS и Reverse VLESS. В обоих режимах маршрутного листа
смысл сервисной карточки остаётся симметричным: она выбирает противоположную
сторону, а не конкретный протокол. DNS VPN-линии следует WireGuard selector.

## Провайдерские подписки и независимые резервы

Поддерживаются plain/base64, VLESS URI, Xray JSON и совместимые смешанные
наборы с VLESS/Hysteria 2. Рабочий процесс:

1. вставить HTTPS URL подписки или добавить независимую VLESS-ссылку;
2. **Получить в черновик**;
3. просмотреть accepted/rejected/deduplicated и причины;
4. при необходимости назначить город вручную;
5. Validate/Promote;
6. сохранить LKG до следующего успешного обновления.

Пустой, повреждённый или полностью отбракованный ответ не заменяет рабочую
копию. URL и UUID в логах редактируются. Сохранённый URL остаётся читаемым в
форме редактирования; ошибка проверки формы не оставляет orphan secret и не
ломает повторное сохранение. До трёх независимых VLESS-резервов можно держать
без подписки; каждая строка открывает полные настройки во всплывающем окне.

## Выбор узла

- **Лучший доступный** выбирает исправный узел с лучшей устойчивой метрикой;
- **Приоритет** выбирает первый доступный пункт пользовательского порядка, а
  внутри пункта — лучший исправный узел;
- один выбранный узел означает отсутствие резерва.

Переход на просто немного более быстрый узел блокируют абсолютный и
относительный пороги, серия успешных проверок и cooldown. Реальный отказ имеет
приоритет. Имена/emoji могут меняться без потери выбора, если endpoint остаётся
тем же; смена server:port требует явного решения.

## Клиентская HTTPS-подписка и экспорт

Клиентский URL содержит все включённые для пользователя варианты:

- VLESS WebSocket/gRPC/HTTPUpgrade/XHTTP через каждый опубликованный CDN;
- прямой VLESS REALITY Vision/gRPC/XHTTP;
- Hysteria 2.

Отдельный CDN endpoint и несколько transport CDN deployment могут делить
TCP/443 по SNI/path. Выбор готового CDN-развёртывания создаёт только новый
секретный путь и не создаёт новый порт. Direct HTTPS занимает указанный WAN
TCP-порт и проверяется на конфликт с direct REALITY.

Один и тот же секретный URL поддерживает пять представлений:

- `?format=links` — base64-набор URI для старых и универсальных клиентов;
- `?format=array` — JSON-массив отдельных Xray-конфигураций и автовыбора;
- `?format=xray` — готовый Xray JSON с TUN, sniffing, DNS, маршрутами,
  fallback, AdBlock и ограничениями LAN;
- `?format=singbox` — нативный sing-box JSON для Hiddify, Karing и sing-box с
  теми же маршрутами, DNS, автовыбором, AdBlock и ограничениями LAN;
- `?format=mihomo` — Mihomo/Clash Meta YAML с теми же пользовательскими
  настройками.

Формат без параметра задаётся в настройках удалённого пользователя. Режим
**Совместимый список** сохраняет URI/base64-набор для обычного клиента, даже
если приложение отправляет общий `Accept: application/json`. Когда у пользователя
включена функция полного профиля, подтверждённые Happ, v2rayNG и V2Box получают
JSON-массив: по одной именованной конфигурации на транспорт и дополнительную
конфигурацию **Автоматический выбор**, если включён клиентский fallback. Полный
одиночный Xray JSON выбирается автоматически только по явному `User-Agent` Xray;
sing-box JSON — по Hiddify/Karing/sing-box, Mihomo YAML — только по известному
Mihomo/Clash-клиенту.
Явный `?format=` имеет приоритет над настройкой пользователя. Заголовок
`X-SB-Profile-Format` сообщает фактически выданный формат. URI-набор содержит
только узлы и не может переносить общую DNS- и маршрутную политику; для неё
нужно выбрать совместимый полный формат. `?format=array` явно запрашивает
JSON-массив для клиента, который его поддерживает.

JSON-массив для Happ, v2rayNG и V2Box содержит локальные SOCKS/HTTP inbounds:
системный VPN/TUN создаёт само приложение. Одиночный `format=xray` для
самостоятельного XrayCore сохраняет нативный TUN, но не закрепляет имя
интерфейса: ядро выбирает его для фактической ОС (`utunN` на iOS/macOS).
В app-managed JSON используется переносимый DNS-блок с `8.8.8.8` и `1.1.1.1`;
списки доменов находятся только в `routing.rules` и не дублируются в DNS.
Транспорт выбирается совместимым полем `streamSettings.network`: старые
встроенные ядра Happ не принимают новое поле `method` для gRPC, Hysteria и
XHTTP. Выбранный в карточке пользователя fingerprint передаётся его
VLESS/REALITY и Hysteria 2 узлам без подмены; совместимость ClientHello с
camouflage target проверяется отдельно. Серверный compatibility-layer принимает
классический X25519 от fingerprint `qq`, не меняя его на другой ClientHello.
QUIC keepalive Hysteria передаётся в полный Xray JSON как
`finalmask.quicParams.keepAlivePeriod`. URI/base64 и Mihomo Hysteria2 не имеют
совместимого поля, поэтому оно туда не добавляется. В sing-box-профиле оно также
не публикуется до повышения минимальной версии клиента: используемое Hiddify
ядро 1.13.1 предшествует общей QUIC-схеме с `keep_alive_period`.
UDP port hopping выключен по умолчанию. При включении полный Xray-профиль получает
клиентскую маску `finalmask.udp[type=udphop]`, ссылка — `mport`, Mihomo — `ports`
и `hop-interval`, sing-box — `server_ports`, `hop_interval` и
`hop_interval_max`. Исключённые занятые порты отсутствуют во всех форматах;
`udphop` всегда стоит перед Salamander как внешняя маска.
Направленный DoH/DNS detour сохраняется в самостоятельных Xray, sing-box и
Mihomo-профилях, где приложение действительно исполняет весь документ. В
sing-box сервисные домены находятся только в `route.rules`, а не копируются в
DNS; домены узлов получают bootstrap resolver через `domain_resolver`.

Автоматический режим проверяется как матрица клиентов, а не как определение
операционной системы по одному слову:

| Клиент | Автоформат с функциями полного профиля | Где выполняется TUN |
| --- | --- | --- |
| Happ (iOS/Android) | Xray JSON-массив | В приложении; JSON содержит SOCKS/HTTP |
| v2rayNG (Android) | Xray JSON-массив | В приложении; 1.9.10–1.9.11 получают URI из-за известной регрессии импорта |
| V2Box (iOS) | Xray JSON-массив | В приложении |
| Hiddify (iOS/Android/Windows/macOS/Linux) | sing-box JSON | В приложении |
| Karing, sing-box CLI/GUI | sing-box JSON | В клиенте; имя TUN выбирает платформа |
| Mihomo, Clash Verge, Stash | Mihomo/Clash Meta YAML | В клиенте |
| XrayCore | Одиночный Xray JSON | Нативный TUN ядра, имя выбирает ОС |
| Shadowrocket, v2rayN, NekoBox, браузер и неизвестные | URI/base64 | В клиенте; общая маршрутная политика не переносится |

Последняя строка намеренно консервативна: совпадение `Accept: application/json`
не доказывает поддержку Xray JSON. Для совместимого клиента администратор может
явно выбрать JSON-массив, Xray JSON, sing-box JSON или Mihomo YAML в настройке пользователя.

Hiddify не получает Clash YAML даже на старых платформах: upstream-регрессия
iOS 4.0.0 удаляет ведущие пробелы удалённого YAML и затем передаёт повреждённый
документ SingboxParser ([hiddify-app #2315](https://github.com/hiddify/hiddify-app/issues/2315)).
Нативные поля VLESS, Hysteria 2, selector/urltest и route следуют
[схеме sing-box](https://sing-box.sagernet.org/configuration/outbound/);
XHTTP сохраняется через используемый Hiddify `xray_outbound_raw`
([пример upstream](https://github.com/hiddify/hiddify-app/issues/2247)).

Уникальный транспорт получает имя без технического порядкового номера. Номер
добавляется только для второго и последующих транспортов одного типа, чтобы
имена узлов оставались различимыми.

В самостоятельном полном Xray/sing-box/Mihomo-профиле DNS-запросы не уходят системному resolver. Домены самих узлов
разрешаются прямым шифрованным DoH по IP — это исключает цикл «для подключения
к VPN сначала нужен уже работающий VPN» и не создаёт plaintext DNS leak.
В Xray/Mihomo исключения используют DNS того же направления, что и их трафик.
В sing-box общий resolver следует направлению основного трафика, transport-
домены всегда используют прямой bootstrap DNS, а сервисные домены не
дублируются в DNS. Внутренние DNS-зоны включаются только когда
выбранный профиль **Доступ к LAN** действительно разрешает соответствующий
DNS/LAN.

При экспорте REALITY публичный ключ вычисляется из активного приватного ключа в
SecretStore. Сохранённое производное поле `public_key` не считается источником
истины и не может оставить XHTTP/gRPC/Vision ссылку на ключ от старой ротации.
Для импортированного legacy-транспорта без ссылки на private secret сохраняется
совместимость с его единственным сохранённым public key.

ZIP-экспорт для администратора дополнительно содержит отдельные JSON/URI и
сводные `client-xray.json`/`client-mihomo.yaml`. Точный набор имён остальных
файлов не считается стабильным API: пользователь выбирает транспорт по
сохранённому названию, адресу и параметрам, а не по внутреннему ID.

Телефон должен использовать TUN/VPN mode. Системный HTTP proxy не охватывает
все приложения и не обеспечивает полноценный доступ к внутренним сервисам.

## Активность и трафик

Обзор считает трафик текущего UTC-месяца отдельно для каждого включённого
локального и удалённого клиента. Скорость — дельта счётчиков между опросами,
а не speed test. `A` означает наблюдаемую активность: Xray online user для
remote либо трафик local за короткое окно.

Счётчики не содержат адреса посещённых сайтов и payload. Ошибка StatsService
или nftables не влияет на маршрутизацию и показывается как недоступные данные.

## Ограничения remote LAN

Для роли с полным LAN-доступом control plane раз в 30 секунд публикует последний
полный успешно обнаруженный snapshot активных RouterOS-маршрутов. Адреса
интерфейсов RouterOS, link-local IPv6 и внутренний container gateway отдельно в
подписку не добавляются. Перекрывающиеся CIDR схлопываются до наиболее общей
доступной сети, поэтому адрес внутри уже опубликованного `/24` не создаёт
лишний `/32`. При неполном или неуспешном опросе продолжает действовать
последний полный snapshot.

Это TCP/UDP proxy, а не L2 bridge. Broadcast, multicast, mDNS и auto-discovery
могут отсутствовать. Внутреннее устройство обычно видит source IP контейнера.
Используйте внутренний DNS и явные IP/ports.
