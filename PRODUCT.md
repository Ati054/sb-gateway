## Platform

## Users

- Владелец или доверенный администратор одного локального либо небольшого офисного шлюза MikroTik.
- Специалист, который помогает установить, проверить или восстановить шлюз.
- Пользователь работает из доверенной локальной сети или через явно разрешённое VPN-устройство. Доступ к панели с WAN и от неразрешённых VPN-клиентов закрыт.
- Сетевые термины допустимы, но знание внутренней схемы конфигурации, порядка RouterOS-скриптов и реализации control plane не требуется.

## Product Purpose

SB Gateway — локальная аутентифицированная панель управления Xray-шлюзом в Linux ARM64 RouterOS Container. Она объединяет клиентов, маршруты, подписки, входящие транспорты, RouterOS-интеграцию, диагностику, резервные копии, Apply и откат. Успешный результат — администратор может безопасно выполнить обычную настройку и понять её фактическое состояние без ручного редактирования RouterOS.

## Positioning

Один интерфейс управляет Xray и принадлежащими SB Gateway объектами RouterOS, сохраняет постороннюю конфигурацию и применяет критические изменения через проверяемый candidate, backup, Safe Mode/fail-open и автоматический rollback. Единственное явное изменение существующего объекта — `allowed-address` выбранного WireGuard peer; исходное значение сохраняется и восстанавливается. WebFig и `gatewayctl` остаются аварийными путями, а не параллельными панелями ежедневной настройки.

## Operating Context

- Настройка выполняется нечасто, но имеет высокую цену ошибки и нередко проводится удалённо.
- Рабочий цикл: черновик → проверка → резервная копия → Apply → readiness → откат при ошибке.
- Администратор сопоставляет панель с реальной конфигурацией RouterOS и должен видеть точный масштаб будущих изменений.
- Релизная проверка охватывает UI, генерацию конфигурации, безопасные операции,
  RouterOS lifecycle и маршрутизацию. Производительность проверяется на целевом
  оборудовании и внешнем узле администратора.

## Capabilities and Constraints

- Текущий контракт релиза: SB Gateway 1.6.18, Xray-core 26.9.9, только `linux/arm64`. sing-box, TUIC и AnyTLS в runtime отсутствуют.
- Поддерживаются VLESS, REALITY, XHTTP, gRPC, HTTPUpgrade, WebSocket и Hysteria 2 в совместимых сочетаниях, включая отдельный прямой `VLESS + gRPC + TLS Pin`.
- Для каждого локального, WireGuard, OpenVPN или входящего VLESS-клиента можно назначить маршрут и поведение при отказе. WireGuard-клиент определяется peer, а не интерфейсом: несколько peers одного интерфейса маршрутизируются независимо, все точные `/32` одного peer объединяются в одну запись, а сохранённая стабильная ссылка переживает изменение адреса peer без дубликата карточки. VPN-сторона маршрута может содержать провайдерские VLESS/Hysteria-узлы, Reverse VLESS и выбранные WireGuard-интерфейсы RouterOS.
- `VLESS + WAN` направляет выбранные сервисы-исключения через WAN; `WAN + VLESS` направляет их через выбранную VPN-политику. WAN и VPN имеют независимые DNS-линии, а пустой набор исключений не создаёт скрытой маршрутизации.
- Публичные DNS-запросы прямого WAN по умолчанию используют Яндекс DNS по DoH. Устаревший выбор RouterOS автоматически переносится на Яндекс DoH; DNS RouterOS остаётся отдельным внутренним резолвером только для локальных зон. Клиентская индивидуальная маршрутизация может включать стратегию `IPIfNonMatch` или ограничиться `AsIs`.
- WireGuard-выход подготавливается автоматически только для трафика SB Gateway: отдельная policy table и source identity не заменяют основной default route MikroTik, а исходный `allowed-address` peer сохраняется для восстановления.
- Новые исключения выбираются карточками или добавляются через доверенный каталог по имени сервиса, домену либо URL. Совместимые старые `direct_domains` сохраняются, но не являются обычным пользовательским вводом.
- Клиентская подписка имеет три сценария публикации: CDN, прямой HTTPS или оба адреса. Внутри CDN-сценария выбирается новый домен либо готовое CDN-развёртывание без нового WAN-порта. Один URL выдаёт совместимый URI-набор, Xray JSON либо Mihomo YAML. Только удалённый VLESS-пользователь может включить **Индивидуальную маршрутизацию**; без неё, а также для LAN, WireGuard и OpenVPN, маршрут исполняется на шлюзе. Полный профиль переносит выбранные исключения через существующие `geosite`/`GEOSITE`-теги и fallback-домены. Составная карточка может раскрыться в несколько тегов; сервер не создаёт тег из её пользовательского названия. Профиль также поддерживает раздельный DNS, клиентский fallback и AdBlock. Локальная сеть устройства сохраняется всегда и не является пользовательской настройкой; это не расширяет заданный в поле **Доступ к LAN** серверный доступ к MikroTik.
- Direct REALITY и CDN/TLS — разные модели безопасности и не описываются как взаимозаменяемые.
- Direct gRPC+TLS Pin использует выбранный TLS-профиль и один pin его текущего leaf-сертификата. TLS-профиль может загрузить пару, получить её через ACME или создать частный `MyRootCA` с десятилетним leaf для одного конкретного SNI. После замены сертификата клиенту требуется обновить подписку.
- Все прямые REALITY-входы используют одну проверку target/SNI: основной SNI проверяется первым, дополнительные конкретные SAN — отдельными TLS-handshake; в конфигурацию попадают только явно выбранные подтверждённые имена.
- Секреты доступны только на замену и не возвращаются браузеру.
- Пароли администратора RouterOS и Web UI не меняются автоматически при Apply,
  обновлении, перезапуске, восстановлении или лабораторной проверке. Смена
  пароля Web UI выполняется только явным запросом владельца с подтверждением
  текущего пароля; пароль RouterOS остаётся под управлением владельца RouterOS.
- Обновление принимает один проверенный Docker ARM64 `.tar`; восстановление использует зашифрованный архив состояния; полное удаление затрагивает только project-owned объекты.
- Возможность считается готовой только тогда, когда её можно найти, настроить, проверить, безопасно применить и понять результат через Web UI.

## Product Principles

1. **Смысл настройки совпадает с результатом.** Никаких фиктивных полей, скрытых маршрутов или успеха без live-подтверждения.
2. **Удалённая настройка остаётся восстанавливаемой.** Опасные изменения имеют точный scope, проверку, backup и автоматический путь возврата.
3. **Интерфейс показывает решение, а не внутреннюю схему.** Понятные названия важнее технических ID; редкие детали раскрываются по запросу.
4. **Посторонняя конфигурация неприкосновенна.** SB Gateway создаёт и удаляет только объекты с подтверждённым владением проекта; обратимое изменение выбранного WireGuard peer допускается только с сохранением исходного значения и автоматическим возвратом.
5. **Полнота важнее преждевременной экономии ресурсов.** Оптимизация не должна ухудшать доступные функции, безопасность или наблюдаемость.
